2.The mental model everything hangs off

Five ideas. Read once; the rest of the guide keeps pointing back to them.

1 · Home network vs the internet Everything on your wifi is your local network (the inside). The internet is the outside. Your router is the guarded door between them, and by default it lets conversations out but blocks uninvited ones coming in. Your server lives inside.
2 · An IP address is a house number Every device has an IP address like 192.168.1.42 so things can find each other. Addresses starting 192.168. (also 10. and 172.16-31.) are private: they only mean something inside your network. The outside world can't see them.
3 · DNS is the internet's phone book Type bbc.co.uk and your device asks a DNS service "what's the number for that name?" and gets an IP back. Pi-hole will be your own phone book that answers normally but refuses to look up ad/tracker names, so ads never load.
4 · A hypervisor makes one computer act like many Proxmox is a hypervisor: software whose whole job is to run several separate virtual computers on one physical box, each walled off from the others. Each little one here is a container.
5 · A snapshot is a save point Proxmox can photograph a container's exact state before you change it. Break something, "roll back", and it's as it was in seconds. This is your safety net and you'll lean on it constantly.
You'll meet this again Ideas 1 to 3 are the core of the CompTIA Network+ and the networking slice of every cloud cert. Idea 4 (virtualization) is the foundation of IaaS in AZ-900: an Azure VM is just a virtual machine on Microsoft's hypervisors instead of yours. Idea 5 is the seed of backup & disaster recovery, a topic in its own right.
Recap
  • Inside (local network) and outside (internet) are separated by the router on purpose.
  • Private IPs identify devices inside; DNS turns names into those numbers.
  • A hypervisor runs many virtual machines/containers on one physical machine; snapshots let you undo.

3.Prep, and the vocabulary to have ready

  • The OptiPlex, RAM and SSD fitted, plugged into power and into your router with an ethernet cable. wired = simpler + steadier
  • A USB stick (2GB+, gets wiped).
  • Your laptop on the same wifi, for the browser side.
  • Your router's admin login (often on a sticker on the router). Find it now.

Understand this: the two kinds of thing you write down Your notes file is about to collect two different kinds of information, and the difference matters more as you go. Most of it is configuration: IP addresses, port numbers, container IDs, which machine does what. None of that is dangerous on its own, and writing it down is pure benefit. A smaller amount is secrets: the root password, keys, and later an API token that can spend money. A secret is anything that grants access rather than describes it, and the rule that follows is simple: a secret is typed once into the machine that needs it, and otherwise lives in your notes file or a password manager and nowhere else. Not in a chat window, not in a screenshot, not in a file you later put on the internet. That distinction between config and secrets is one of the first things any real deployment separates out, and you'll see this guide keep them apart deliberately from here on.
Understand this: why wired matters An always-on server on wifi has to keep re-negotiating a radio link that drops and shares airtime with everything else. A wired ethernet connection is a dedicated, stable path. In a data centre or the cloud, servers are never on wifi for exactly this reason. Small detail, real-world principle.
Part 2 · Build the machine and its core services

4.Installing Proxmox: meet the hypervisor

Understand this before you start: what is Proxmox? Proxmox VE is a free operating system built on Debian Linux whose job is to be a Type 1 hypervisor. "Type 1" means it installs directly onto the bare hardware and the virtual machines run on top of it (as opposed to "Type 2" like VirtualBox, which runs as an app inside Windows). Type 1 is what real servers and clouds use because there's no extra operating system in the way stealing performance. You're installing the same class of software that runs Azure, AWS and Google Cloud, just the home edition.

Step A, make the install USB you do this by hand

  1. On your laptop, go to proxmox.com → Downloads → Proxmox VE, and download the .iso file.
    What an ISO is: a single file that is an exact image of an install disc. It contains the whole operating system, ready to be written to a USB and booted.
  2. Download balenaEtcher from balena.io/etcher, open it, choose Flash from file → the ISO, Select target → your USB stick (check it's the stick!), then Flash.
    Why not just copy it on: a bootable stick needs the data written in a special low-level layout the computer can start from, which Etcher does. Copy-paste wouldn't boot.
    You'll see: "Flash Complete." The stick is now an installer.

Step B, install onto the OptiPlex by hand

  1. Insert the stick, power on, tap F12 repeatedly, and pick the USB from the boot menu.
    What's happening: the "boot menu" lets you choose which drive the machine starts from this once. Normally it starts from its internal drive; you're telling it to start from your installer instead.
  2. Choose Install Proxmox VE (Graphical) and accept the licence.
  3. Target drive: choose your Crucial SSD (check the size looks right, ~480GB).
    Understand this: the installer will format this drive and lay down a Linux filesystem plus Proxmox. "Format" means wipe and set up a fresh filing system. It's the one destructive moment, hence the check.
  4. Country / timezone / password / email: set a strong root password (write it down) and any email.
    Who "root" is: on Linux, root is the all-powerful administrator account (the equivalent of full admin on Windows). This password guards total control of the machine, so it matters.
  5. Network screen: note the IP Address it shows (e.g. 192.168.1.50). Accept sensible defaults for the rest.
    Why write it down: that address is how you'll reach the server from your laptop. It's the front-door number for everything from here on.
  6. Click Install, let it finish, and remove the USB as it reboots.
    You'll see: a blue screen ending with something like https://192.168.1.50:8006. That's your control panel address. The machine can now run "headless" (no monitor or keyboard).
Understand this: "headless" and why servers are like it A headless machine has no screen, keyboard or mouse; you administer it entirely over the network from another device. Nearly all servers on Earth are headless, sitting in racks nobody looks at, managed remotely. You just set one up. That web address on port :8006 is your remote management console.
You'll meet this again This is IaaS (Infrastructure as a Service) from the ground up, an explicit AZ-900 topic. When Azure gives you a VM, they've done what you just did (hypervisor on hardware) and handed you the "create a virtual machine" button. You now know what's behind that button.
Recap
  • Proxmox is a Type 1 (bare-metal) hypervisor built on Debian Linux.
  • An ISO is a bootable disc image; you flashed it to USB to install from.
  • root is the Linux super-admin; servers run headless, managed over the network on a port.
Check yourself

Q1. What's the difference between a Type 1 and Type 2 hypervisor?

Type 1 runs directly on the hardware (Proxmox, ESXi, Azure's); Type 2 runs as an application inside an existing OS (VirtualBox). Type 1 is faster and used for servers/cloud.

Q2. You set a password for an account called "root". What is root?

The all-powerful administrator account on a Linux system, with complete control over the machine.

5.First login: Linux, packages and the command line

  1. On your laptop browser, go to your https://192.168.1.50:8006 address (include https:// and :8006).
    What the :8006 means: a single machine can run many services at once, so each listens on a numbered port, like flat numbers at one street address. Proxmox's web console lives on port 8006. You'll see this idea everywhere.
  2. The browser warns "not private". Here that's expected: click Advanced → Proceed.
    Understand this: that warning means the site's security certificate isn't signed by a public authority. For a public bank site that'd be alarming; for your own machine on your own network it's normal, because no public authority has vouched for your private box. The connection is still encrypted.
  3. Log in with root and your password. Dismiss the "No valid subscription" notice (it's an optional paid support plan).
    You'll see: the Proxmox dashboard. On the left is your server ("node"); clicking it reveals tabs.
  4. Click your node, then Shell. A black terminal opens. Type hostnamectl and press Enter.
    What you just did: the Shell is a command-line terminal on the server itself. hostnamectl prints system info. You're now "in" a Linux machine, typing commands, the way most of the server world is actually run.
  5. Find out where you are standing, and what is around you: pwd ls -la
    You'll see: /root from the first, and a short listing from the second. pwd is print working directory, and ls lists what is in it. The -l asks for the detailed one-per-line form and the -a includes hidden entries.
  6. Now look at the top of the filesystem instead, without moving: ls -la /
    You'll see: a completely different and much longer list, with etc, opt, media, home and others.
Understand this: where a command looks, and the two ways to say where Every command you type happens somewhere. When you log in you are placed in /root, the root user's own folder, and a bare ls lists that and nothing else. This catches people out constantly: you know a folder exists, you run ls, it is not there, and the folder is fine. You were simply standing somewhere else. It is the same as opening your Documents folder and being surprised not to find Program Files in it.

There are two ways to name a location, and the difference is one character. A path beginning with a slash, like /media, is an absolute path: start at the very top of the filesystem and work down, which means the same place no matter where you are standing when you type it. A path with no leading slash, like media, is a relative path: a folder of that name inside wherever you happen to be right now. So cd /media always works and cd media only works if you are in the one place that contains it.

Two shorthands go with this and appear constantly: . means "right here" and .. means "one level up", so cd .. steps back out of a folder. When something does not behave as expected, pwd is almost always the first thing worth typing.
Understand this: how Linux installs software (this is a big one) On Windows you download an .exe and double-click. Linux mostly uses a package manager: a built-in tool that fetches software from trusted online repositories (curated software libraries) and installs it with dependencies handled for you. Proxmox is Debian-based, so its package manager is apt. Two commands do almost everything: apt update # refresh the list of available software apt upgrade # install newer versions of what you have This is one of the most useful things you can learn, because every Debian/Ubuntu server on the planet works this way.

The one setup script, and what it's actually doing script for speed, explained fully

  1. Open community-scripts.org, find Proxmox VE Post Install, copy the command into the Shell, run it, accept the sensible defaults, and reboot when asked.
    What it does under the hood, so you learn it: a fresh Proxmox is configured to use the enterprise software repository, which needs a paid subscription, so updates fail and it nags you. The script switches you to the free no-subscription repository and turns off the nag. In plain apt terms it's editing the repository list (files under /etc/apt/) and running apt update. You could do it by hand; the script just saves fiddly typing.
    You'll see: text scrolling as it edits repositories and refreshes, then a reboot prompt.
The rule for the Shell (a real security habit) Only paste commands from an official project's own site (community-scripts.org, or a vendor's own domain like tailscale.com later). Pasting a command you don't understand from a random forum is exactly how people get compromised. "Don't run untrusted code as root" is a principle you'll see stated formally in every security course.
You'll meet this again Package managers, repositories and the command line are day-one Linux skills. They're the core of CompTIA Linux+ and assumed knowledge for AZ-104, DevOps, and cloud engineering (cloud servers are overwhelmingly Linux). The comfort you build typing in this Shell is directly transferable and genuinely uncommon at entry level, so it stands out.
Recap
  • Services listen on numbered ports (Proxmox = 8006); one machine, many services.
  • The Shell is a Linux command line on the server; you ran your first commands.
  • Linux installs software via a package manager (apt) from repositories; the post-install script just automated a repo change.
Check yourself

Q1. What does apt update do, and how does it differ from apt upgrade?

apt update refreshes the list of what software is available; apt upgrade actually installs the newer versions. Update = check, upgrade = apply.

Q2. Why does the browser warn that Proxmox "isn't private", and why is it fine here?

Its security certificate isn't signed by a public authority (it's self-signed for a private machine). It's fine because it's your own server on your own network; the connection is still encrypted.

6.Your first container + Pi-hole: containers & networking

This is the richest learning section, so we build the container by hand (it's the single best way to understand virtualization), then install Pi-hole inside it and learn how networks actually resolve names.

Understand this: container vs virtual machine Both give you an isolated "computer", but differently. A virtual machine pretends to be a whole physical PC and runs its own complete operating system, so it's heavier. A container shares the host's Linux core (kernel) and just isolates the software on top, so it's much lighter and starts in seconds. Proxmox's containers use LXC. Rule of thumb: containers for lightweight Linux services (like Pi-hole), VMs when you need a full separate OS (like Windows). This exact trade-off is a huge topic in industry, where Docker and Kubernetes made containers the default way to ship software.

Step A, create your first container by hand you do this by hand

  1. In Proxmox, first get a "template" (a ready-made mini OS to base the container on): click your node → local (storage) → CT Templates → Templates, and download debian-12-standard.
    What a template is: a pre-built base image of a minimal operating system. Your container starts as a copy of it, so you're not installing an OS from scratch each time. Cloud works the same way ("images").
  2. Top-right, click Create CT (CT = container). Give it a hostname like pihole, and set a password for inside the container.
  3. Choose the debian-12 template you downloaded. For resources, modest is fine: 1 CPU core, 512MB memory, 4GB disk.
    Understand this: you're carving off a slice of the physical machine's cores, memory and disk to give this little computer. This is exactly what "sizing a VM" means in the cloud, where you pick how much CPU/RAM to rent. Pi-hole is tiny, so it needs almost nothing.
  4. On the network screen, leave it to get its address automatically (DHCP) for now, finish the wizard, and Start the container.
    What DHCP is: "Dynamic Host Configuration Protocol", the service (usually on your router) that automatically hands out IP addresses to devices that join the network, so you don't set them by hand. Your phone, laptop and now this container all get theirs this way.
    You'll see: your container listed in the left panel, and under its Summary the IP it was given, e.g. 192.168.1.51. You built a working computer in about two minutes.
Pin its address (so networking stays predictable) Because the whole house will soon rely on Pi-hole's address, it shouldn't change. Easiest way: in your router, find DHCP reservation and tie Pi-hole's address to it permanently. Why this matters technically: DHCP leases can change over time; a reservation (or a manually set "static" IP) guarantees a fixed number. Servers almost always get fixed addresses for this reason.

Step B, install Pi-hole inside the container

  1. Select the container → Console, log in as root with the password you set, and run Pi-hole's official installer: curl -sSL https://install.pi-hole.net | bash
    What this line means, piece by piece: curl downloads a file from a web address; the | ("pipe") feeds that downloaded script straight into bash, which runs it. It's from Pi-hole's official domain, so it's trusted. Follow the prompts, accepting defaults; when it offers an upstream DNS provider pick one like Cloudflare.
    You'll see: a blue setup wizard, then a final screen giving you the admin web address (http://192.168.1.51/admin) and a password. Write both down.
Understand this: what actually happens when you open a website This is the concept Pi-hole teaches, and it's gold for interviews and certs. When you type bbc.co.uk: 
your device ──"what's the IP for bbc.co.uk?"──▶ Pi-hole (your DNS resolver)
      │                                              │
      │                          is it on the ad/tracker blocklist?
      │                          ├─ yes ▶ reply "nothing here" (ad never loads)
      │                          └─ no  ▶ ask an upstream DNS (e.g. Cloudflare)
      │                                     which returns the real IP
      ◀──────────── real IP (e.g. 151.101.0.81) ─────────────┘
your device then connects to that IP to load the page
DNS runs on port 53. Pi-hole is simply a DNS resolver that consults a blocklist first. That's the entire trick, and now you understand it properly.

Step C, roll it out safely (test on one device first)

This is the one change that touches the whole household, so we de-risk it exactly like a professional would: test on a single device, keep the undo ready, then roll out.

  1. Test on your phone only: phone wifi settings → your network → DNS → switch to Manual → enter Pi-hole's IP (192.168.1.51). Browse.
    You'll see: sites load, many ads vanish, and Pi-hole's dashboard counter climbs. Proof, affecting nobody else.
  2. Then roll out to everyone: log into your router, find the DNS server setting, note the current value, and replace it with Pi-hole's IP. Save, then reconnect a device.
    Why the router: it hands out DNS settings to every device via DHCP, so changing it once points the whole house at Pi-hole automatically.
If it goes wrong (know this before you touch the router) If the house can't load sites, set the router's DNS back to Automatic / the value you noted. Everyone is back to normal within a minute. This never touches your actual internet line, only which phone book devices consult, so it's fully reversible. Also good to know: if you later shut the server off for a while, switch the router DNS back first, or the house will struggle to look names up until it returns.
You'll meet this again DNS, DHCP, ports and IP addressing are the backbone of CompTIA Network+ and appear in every cloud platform: Azure has Azure DNS and hands out private IPs to VMs inside virtual networks exactly like your router does at home. "It's always DNS" is the industry's favourite troubleshooting joke because DNS problems are so common; you now know why.
Recap
  • Containers are lightweight isolated computers sharing the host kernel; you built one from a template and sized its CPU/RAM/disk.
  • DHCP auto-assigns IPs; a reservation pins one so servers stay findable.
  • DNS resolves names to IPs on port 53; Pi-hole is a resolver that filters a blocklist first.
  • You rolled out a network-wide change the safe way: test one device, keep the undo, then apply.
Check yourself

Q1. A container and a VM both isolate a workload. What's the key technical difference?

A VM runs its own full operating system (heavier); a container shares the host's kernel and only isolates the software on top (lighter, faster to start).

Q2. Walk through what DNS does when you visit a site, in one sentence.

Your device asks a DNS resolver for the IP address behind the name, and once it gets the number it connects to that IP to load the page.

Q3. Why give the Pi-hole container a reserved (fixed) IP?

Because the whole network will point at that address for DNS; if DHCP changed it, lookups would break. Servers need predictable addresses.

7.Jellyfin: watching your media (clients, servers, ports and direct play)

You've built a container once, so this reinforces it, then teaches the client/server model and the single most important idea in running your own media server: making sure the server never has to work hard. Nothing here affects the household. You are building the player first and giving it a library in the next section, because the library setup needs a container to point into and this is that container.

  1. Create a second container the same way (or, since it's fiddlier to wire up the media drive and graphics, use the community-scripts.org Jellyfin helper and say yes when it offers hardware acceleration). Either way you'll get a Jellyfin address ending :8096.
    Why a helper is fine here: Jellyfin plus graphics passthrough is exactly the "fiddly, low-learning" bit where a script earns its keep. You already learned container-building by hand with Pi-hole earlier; nothing lost.
  2. Write down two things before you move on: the container's ID number (the number Proxmox shows next to it in the left-hand list, usually 101 or similar), and how you created it, by hand or via the helper script.
    Why you'll want these: the next section addresses the container by that number, and the one permissions problem you might hit there has two different fixes depending on which way you made it. Thirty seconds now saves a confusing ten minutes later.
  3. Open the :8096 address and create your admin account. When the setup wizard asks you to add a media library, skip it and finish the wizard; you'll come back and add it properly in the next section.
    Why skip it: the folder you want to point at doesn't exist inside this container yet. Adding a library now means pointing at an empty path and then editing it later, which is just the same job done twice.
  4. Install a Jellyfin app on a phone or computer, enter the server address and sign in. Which app you pick is a real decision, not a formality, so take it from this list rather than searching the store for "Jellyfin" and tapping the first result:
    • iPhone or iPad: Streamyfin
    • Android phone or tablet: Findroid
    • Windows or Mac: Jellyfin Media Player, which is a proper installed program, not the web page in a browser tab
    • Samsung or LG smart TV: the official Jellyfin app, or Moonfin. TVs are the one place with no better option, because those platforms are closed and nobody can build a better player for them
    Why this list and not the obvious one: the official mobile apps and the browser player are built on web technology, which is only allowed to play the handful of video formats the browser itself understands. Anything outside that list gets refused, and refusing is what forces your server into the expensive work described in the box below. The three apps named above are built around MPV, a playback engine that decodes essentially any format that exists, so they refuse almost nothing. The choice of app decides how hard your server has to work, which is not something you'd guess from an app store listing.
    You'll see: an empty library and a working connection. Empty is the correct result at this point. Proving the app reaches the server now means that if something breaks after you add the drive, you already know the network side was fine.
Understand this: the client/server model, and why "direct play" is the whole goal Jellyfin shows you the pattern behind almost all software you use. The server (on your box, port 8096) holds the data and does the work; the client (the app on your TV) requests it. Your web browser and websites, your email app and mail servers, all work this way.

When somebody presses play, one of two things happens, and the gap between them is enormous. In direct play, the server hands the file over exactly as it is and the app does all the decoding itself. The server is barely working, it's doing little more than copying a file across the network. In transcoding, the app says it cannot handle this file, so the server rebuilds the video into a different format on the fly, frame by frame, for the entire length of whatever is being watched.

So transcoding is not a feature you're aiming to use. It's a rescue. It's where nearly every complaint about stuttering, buffering and a noisy machine comes from, and here's the part that surprises people: it's almost always triggered by the app being incapable, not by the server being weak. A better app on the same server, playing the same file, simply doesn't ask for it.

You'll also see hardware acceleration mentioned constantly in Jellyfin's world, and specifically Quick Sync, a dedicated video-processing circuit built into Intel chips that does conversion work far more efficiently than the general processor. Switching it on is worth doing because it's a single checkbox and costs nothing. Just be clear about what it is: it makes a bad outcome less painful. It doesn't make transcoding a good idea.
You'll meet this again Client/server, ports and services are foundational to everything. The other idea sitting inside this section, handing a particular kind of work to purpose-built hardware rather than the general processor, is exactly why cloud providers rent GPU instances and why AI runs on graphics chips. When AZ-900 lists Azure's specialised compute options, you'll recognise the shape of it. But the bigger lesson is the one worth carrying into any job: the cheapest way to make a system fast is to stop asking it to do work it never needed to do.
Recap
  • Software is mostly client/server: a server provides, a client consumes, over a port.
  • Direct play means the server hands the file over untouched and the app decodes it. That's the target, every single time.
  • Transcoding is the server rebuilding the video on the fly because the app can't cope. It's the expensive fallback, and the usual cause is a weak app rather than a weak server.
  • Which app you install therefore decides which of the two you get, which is why Streamyfin, Findroid and Jellyfin Media Player are named specifically.
  • Quick Sync is worth enabling as a safety net, but it improves the fallback rather than removing the need for one.
Check yourself

Q1. In the client/server model, which side is the Jellyfin app on your phone, and which side is on your OptiPlex?

The phone app is the client (requests and plays); the OptiPlex runs the server (stores the media and serves it).

Q2. What's the difference between direct play and transcoding, and which one are you aiming for?

Direct play hands the file over untouched and lets the app decode it, so the server does almost nothing. Transcoding makes the server rebuild the video on the fly because the app can't handle it. Direct play is the target; transcoding is a rescue you want to avoid triggering.

Q3. A film stutters and the machine gets loud. What should you suspect first, and where's the fix likely to be?

That it's transcoding. The fix is usually at the app rather than the server, because a more capable app would have played the same file as it was.

A nicer way to watch: the Fladder app

What this actually is Jellyfin already has its own apps and its own web page. Fladder is simply a different app, built by a different team, that talks to the exact same Jellyfin server underneath. Nothing about your library, your accounts, or your files changes by adding it, it's a different front door onto the same building, not a new building.

It can be added as its own small container using the same community-scripts pattern as before, run from the Proxmox host:

bash -c "$(curl -fsSL https://raw.githubusercontent.com/community-scripts/ProxmoxVE/main/ct/fladder.sh)"

Accept the defaults, open the address it gives you, and point it at your existing Jellyfin server and account. Worth trying for two genuinely useful things the standard Jellyfin apps don't do as well: real offline downloads (so a film keeps playing with no connection at all, useful on a journey), and automatic skipping of intros and credits. It's optional polish, not a required piece, so it's fine to skip for now and come back to it.

8.Storage: the big drive, and getting it inside the container

Your SSD runs the system; this new hard drive holds files. Jellyfin exists now but has nowhere to look, so this section prepares the drive, attaches it into Linux, and opens a controlled doorway from the host into the container you just built. Four jobs in order: make the drive usable, mount it, share it in, then point Jellyfin at it.

What actually ends up on this drive Worth setting expectations, because it changes what size you need. Later in this guide your film and series library is streamed on demand rather than downloaded, so the library itself takes up almost nothing: a few kilobytes per title. This drive is for the things that do live on your machine, which is anything you own or rip yourself, your Jellyfin metadata and artwork, container backups, and the record the streaming setup keeps of what it can offer, which is a database entry per title rather than a file. You still want a proper drive and you still need every skill in this section, but you are not filling eight terabytes with films, and you should not buy on that assumption.
Understand this: SSD for the system, hard drive for the data Two jobs, two kinds of drive. Your SSD is fast but small: ideal for the operating system and apps that do constant small reads and writes. Your NAS hard drive is big and cheap per terabyte: ideal for bulk media that's read in long steady streams and doesn't need speed. Splitting "fast small disk for the system" from "big cheap disk for the data" is a standard design you'll see everywhere, including cloud VMs, which pair a small OS disk with larger attached data disks for exactly this reason.

Step A, fit the drive by hand

  1. With the machine off, connect the hard drive's SATA data and SATA power cables (same as the SSD) and secure it. Power back on.
    Why alongside, not instead: the SSD stays as your system drive; this is a second, separate drive purely for files.

Step B, put a filesystem on it by hand, strong learning

Understand this: raw disk vs filesystem A brand-new drive is just raw empty space; the system can't store files on it until you put a filesystem on it. A filesystem is the organising structure (folders, names, where each file physically lives) that turns raw space into something usable, like fitting an empty warehouse with labelled shelving. "Formatting" means laying that structure down. Windows uses one called NTFS; Linux most commonly uses ext4, which is what you'll use.
  1. In the Proxmox Shell, list the drives to find the new one: lsblk
    Reading it: this lists every disk with its size. Your SSD (~480G, with Proxmox on it) will be there; the empty ~8T disk is the new one, most likely called /dev/sdb. Note its name carefully: the next command wipes whatever you name.
  2. Format the new drive with ext4 (swap sdb for whatever lsblk showed): mkfs.ext4 /dev/sdb
    What this does: writes the ext4 filesystem onto the drive, making it ready to hold files. It erases the drive, which is fine because it's new and empty. This is exactly why you double-checked the name first.

Step C, mount it into Linux

Understand this: mounting, and Linux's single tree Windows gives each drive its own letter (C:, D:). Linux is different, and once it clicks, cleaner: there is one folder tree starting at / (the "root"), and you mount a drive into that tree at a folder of your choosing. Your media drive won't be "D:"; it'll appear as, say, /mnt/media. Mounting is simply attaching a drive to a chosen spot in the tree.
  1. Make a folder to mount it at, and mount it: mkdir -p /mnt/media mount /dev/sdb /mnt/media
    You'll see: nothing dramatic, which means success. Run df -h and your ~8T drive now shows against /mnt/media. It's part of the filesystem.
  2. Make it mount automatically at every boot. First get the drive's unique ID: blkid /dev/sdb Copy the UUID="..." value it prints. Open the config file in the built-in editor: nano /etc/fstab add this line at the bottom (paste your UUID in place of the x's), then save with Ctrl+O, Enter, Ctrl+X: UUID=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx /mnt/media ext4 defaults 0 2
    What fstab is: a file listing drives Linux should mount automatically at startup. Without this line, the drive would disappear after a reboot and Jellyfin would lose its library. Editing config files like this by hand is a big part of real Linux administration, so this is good practice, not just a chore.

Step D, open a doorway into the Jellyfin container (bind mount)

Understand this: why the container can't see the drive yet Remember, a container is deliberately walled off from the host; that isolation is the point. So even though the host can now see /mnt/media, your Jellyfin container cannot, by design. You open one specific, controlled doorway called a bind mount: it makes a single host folder appear inside the container. You're not exposing the whole host, just sharing the one media folder in.
  1. Use the Jellyfin container ID you noted in the previous section (e.g. 101), then from the host Shell attach the folder into it: pct set 101 -mp0 /mnt/media,mp=/media
    Reading it: pct is Proxmox's container tool. This says "for container 101, add mount point 0: share the host's /mnt/media so it appears inside as /media." Now your big drive is visible at /media from inside Jellyfin.
  2. Restart the container so it picks the new mount up, then check it landed: pct reboot 101 pct exec 101 -- ls -la /media
    You'll see: a listing of the folder. If it says No such file or directory, the mount point didn't apply, so re-check the container number in the command above.
You may hit this here: the container can see the folder but can't read it This is the one predictable snag in the whole section, so here it is before it happens rather than after. For security, "unprivileged" containers remap their internal user accounts to different numbers on the host. The folder appears inside the container, but the container's own user may not own it, so Jellyfin finds an empty library or throws a permission error when it scans. The symptom is a library that scans instantly and finds nothing, even though you can see the files from the host. The fix is a one-line ownership or ID-mapping change, but which one depends on whether you made the container by hand or with the helper script, which is why you wrote that down. If you see it, say so and fix it deliberately rather than guessing; it's a thirty-second job once you know which case you're in, and permission models like this are worth understanding rather than working around.

Step E, point Jellyfin at it

  1. Make a folder on the drive for the things you actually own, from the host Shell: mkdir -p /mnt/media/films
    Why a subfolder and not the drive root: a mounted ext4 drive has a lost+found folder at its top level, and pointing a library straight at the root means Jellyfin tries to scan that too. Keeping libraries in named subfolders also means one drive can hold several without them getting tangled.
  2. In Jellyfin's web page, go to Dashboard, then Libraries, add a library and set its folder to /media/films. Copy a video file or two onto the drive and let it scan.
    You'll see: your files appear in Jellyfin, served from the big drive. Play one, ideally in a browser first, to confirm the whole chain works before you involve a TV app.
You'll meet this again Filesystems, mounting, /etc/fstab and the single-tree layout are core Linux fundamentals, straight out of CompTIA Linux+. The "OS disk plus data disks" split is how storage works on cloud VMs. And editing a config file like fstab by hand is the everyday reality of Linux and cloud administration, so this section punches above its weight for learning.
Recap
  • SSD holds the system; the big NAS drive holds bulk media. Different jobs, different drives.
  • A raw drive needs a filesystem (ext4) before it can store files; formatting writes that structure.
  • Linux mounts drives into one folder tree; fstab makes it happen automatically at boot.
  • A bind mount shares one host folder into an isolated container; unprivileged containers may need a permissions tweak.
Check yourself

Q1. Why use the SSD for the system but the hard drive for media?

The SSD is fast but small, ideal for the OS and apps doing many small reads/writes; the hard drive is big and cheap per terabyte, ideal for bulk media read in steady streams, which doesn't need SSD speed.

Q2. What does "formatting" a new drive actually do?

It writes a filesystem (like ext4) onto the raw disk: the structure that lets the system store and find files. Until then the drive can't hold anything.

Q3. The Jellyfin container can't see the drive even though the host can. Why, and what opens it up?

Containers are isolated from the host by design, so they can't see host drives automatically. A bind mount shares a specific host folder (here /mnt/media) into the container (as /media).

9.Remote access: the whole of home networking, and security

Reaching your server from outside is where the whole of home networking finally clicks. We'll do it the way that actually sticks: get the picture in plain terms first, then put the proper names to each piece once it makes sense.

The picture, in plain terms

When you're out of the house, you want your phone to reach your stuff at home. Picture your setup as an apartment building on a street:

  • Your one physical machine is the building.
  • Jellyfin and Pi-hole are flats inside it. Here's the bit that trips people up: even though they share the one machine, each flat has its own address on the street (that's what a container is, its own little computer with its own number).
  • The base system that runs the whole box is the front desk.
  • A badge is a pass that lets a device into a private, invite-only tunnel. Only your phone and the front desk have one.

So when you're away: your phone (with its badge) travels down a private tunnel to the front desk. The front desk can knock on any flat's door because they're all in the same building, so it passes you through to Jellyfin or Pi-hole, even though those flats have no badge of their own. That "make the front desk pass me through to the flats" bit is the one step people find confusing, and it really is all it is.

But how does that private tunnel actually get made, without ever opening the front door? Through a switchboard (a matchmaker). Both your phone and your home keep a line dialled out to the switchboard at all times, and dialling out is always allowed. When you want in, the switchboard checks that both are on your guest list, introduces them, and a private tunnel forms straight between the two. Because both sides reached outward first, the main front door never has to open at all. That last point is the whole reason it is safe.

Why none of this is sitting on the public internet

In plain terms: your home is a house with a single front door to the street, and that door only opens outward. Your devices can start conversations going out, but the street can't wander in uninvited. Putting servers inside the house doesn't unlock that door.

The names: NAT and a stateful firewall Your whole home shares one public IP address from your provider; inside, each device has a private IP. The router does NAT (Network Address Translation), letting many private devices share that one public address for outbound traffic, and it runs a stateful firewall that only lets back in the replies to conversations your devices started. Anything inbound that nobody asked for is dropped. That's the "door only opens outward", said properly, and it's why your server isn't reachable from outside by default. Not luck, just how these work.
The one thing never to do (and its name) Online you'll be told to switch on port forwarding to reach your server. In plain terms, that props your front door open to the entire street. In proper terms, it exposes a service straight to the whole internet, where bots constantly scan for exactly that, and it widens your attack surface (a real security term). We never do it. Tailscale gets you in without ever opening the door.

Set it up good command-line practice

  1. Make a free account at tailscale.com (sign in with an existing Google/Microsoft login).
    Plain version: this creates the "club" that only your own badged devices are allowed to join.
  2. In the Proxmox Shell, install and start Tailscale on the host (the front desk) with its official commands: curl -fsSL https://tailscale.com/install.sh | sh tailscale up
    Reading the commands: same pattern as Pi-hole, curl fetches the official installer and pipes it into a shell to run. tailscale up links this machine to your account. It prints a link; open it on your laptop to approve. This is you giving the front desk its badge.
  3. Now make the front desk a doorway to the whole home (find your range from the host's IP: 192.168.1.50 gives 192.168.1.0/24, the first three numbers of your own host's address followed by .0/24): tailscale up --advertise-routes=192.168.1.0/24 --accept-dns=false then approve that route once in the admin page at login.tailscale.com.
    This is the "pass me through to the flats" step from the diagram. --advertise-routes=192.168.1.0/24 hands the front desk the whole home "street" to forward you onto, and the approval click is just you confirming you're happy for it to. That's all the scary-looking line does.
    If you see warnings about "forwarding disabled": Tailscale is telling you the machine's own underlying ability to pass traffic through to other devices is switched off by default, a separate, lower-level Linux setting from anything Tailscale itself controls, and a sensible default since most computers only ever handle traffic meant for themselves. Turn it on with: echo 'net.ipv4.ip_forward = 1' | tee -a /etc/sysctl.d/99-tailscale.conf echo 'net.ipv6.conf.all.forwarding = 1' | tee -a /etc/sysctl.d/99-tailscale.conf sysctl -p /etc/sysctl.d/99-tailscale.conf No need to redo the tailscale up command afterward, this fixes a separate permission underneath it. A second warning about UDP GRO on your bridge is just a performance tweak, not a correctness problem, safe to leave alone.
  4. Install the Tailscale app on your phone, sign into the same account, toggle it on. Turn wifi off (mobile data) and open Jellyfin at its home :8096 address.
    You'll see: it plays over mobile data, through the private tunnel, nothing exposed to the public. Lose a phone? Remove it in the admin page and it instantly loses all access.
  5. Try one of your memorable addresses instead, like nadrijellyfin.com, while still away from home on mobile data. This one will not load yet, and that is expected.
    Why the plain IP address works but the memorable name does not: a name like nadrijellyfin.com only means anything because Pi-hole is the one answering for it. Your phone only learns to ask Pi-hole for DNS answers because your home router's DHCP hands that instruction out automatically, and that only happens to devices actually connected to your home network. A phone out on mobile data, even through the Tailscale tunnel, never received that instruction, so it falls back to the regular public internet's DNS, which has never heard of nadrijellyfin.com and fails.
    The fix, done once in the Tailscale admin console: on a computer, go to login.tailscale.com and click DNS in the sidebar. Under Nameservers, add a Global Nameserver and enter Pi-hole's address (192.168.1.97). Switch on Override DNS servers underneath it, then save. This is Tailscale's own way of doing the same job your router's DHCP normally does, but for devices that are only ever reachable through the tunnel: it tells every device in your tailnet "for DNS questions, ask this address," the same instruction your router already gives phones at home. Afterward, on the phone, toggle Tailscale off then on again so it picks up the new setting, and try nadrijellyfin.com again on mobile data. It should now resolve exactly like it does at home.

That's a serious chunk of Network+ and Security+, and the networking concepts in AZ-900/AZ-104 (VNets, Network Security Groups, VPN Gateway) are the same ideas at cloud scale. You'll walk into that material already fluent.
Recap
  • NAT + a stateful firewall are why your server isn't public by default; inbound uninvited traffic is dropped.
  • Port forwarding deliberately exposes a service and widens your attack surface; we avoid it.
  • A VPN (Tailscale/WireGuard) gives safe remote access via an invite-only encrypted overlay: zero-trust.
  • CIDR like /24 describes a block of addresses; the same notation runs cloud networks.
Check yourself

Q1. Your server has never had port forwarding set up. Explain to a mate why a hacker on the internet can't just connect to it.

The router uses NAT and a stateful firewall: it only lets in replies to connections your own devices started. Unsolicited inbound traffic from the internet is dropped, so the server isn't reachable from outside.

Q2. Why is a VPN like Tailscale safer than port forwarding for remote access?

Port forwarding exposes a service to the entire internet. A VPN creates an encrypted, invite-only tunnel that only your own devices can join, so nothing is publicly reachable.

Q3. Jellyfin and Pi-hole run on the same machine as the host, so why does the host still have to "forward" your phone to them?

Because each container has its own address on the network, and only the host has Tailscale. Your phone reaches the host through the tunnel, and the host passes it on to those containers by their own addresses. That forwarding is subnet routing.

Q4. What does /24 mean in 192.168.1.0/24?

CIDR notation for a block of 256 addresses (192.168.1.0–.255), where the first 24 bits are the fixed network portion.

10.Filling your library on its own: Gelato, a streaming engine, and no downloads

Up to now, getting a new film or show into Jellyfin has meant finding it, downloading the whole file, and storing it on your own disk. This section takes a completely different route to a library that keeps itself current: instead of downloading and keeping anything, your server lists every title you could want, thousands of them, and only pulls the actual video from a fast streaming source at the moment someone presses play. The payoff is an enormous library that fills itself with no downloading, no waiting overnight, and no half finished files, in exchange for leaning on an outside service to do the heavy lifting. That trade is a real one, so it is spelled out plainly below before anything gets set up.

Understand this: warehouse versus shop window The old download approach is a warehouse. Every title physically arrives and sits on your shelves, yours forever, playing even with the internet down, but slow to fill and hungry for disk space. This new approach is a shop window. Your library shows a card for every title, thousands of them, but nothing is actually in the back room until someone asks, at which point it is fetched and played in seconds. Those cards are not files. Each one is a row written straight into Jellyfin's own catalogue, the same database that already tracks everything you own, marked as a title whose video lives elsewhere. Almost nothing lands on your disk at all. Because nothing is stored, nothing stalls the way that Rick and Morty download did, but the shop only works while its supplier is open.
Understand this: the three pieces that make it work Three parts do this between them, each with one clear job. A debrid service (this build uses TorBox) is the engine: a company that keeps a huge pile of already fetched content sitting on fast servers and hands it to you over an ordinary web connection, which is exactly why playback is instant and there is no seeding or stalling to babysit. AIOStreams is the adapter: it gathers dozens of separate streaming sources, tidies and de-duplicates them, and hands your server one clean feed instead of a mess of eighty. Gelato is the Jellyfin plugin that ties it together: it writes the cards into your library catalogue, and when someone hits play it asks AIOStreams for a stream, gets one served from your debrid engine, and pipes it through Jellyfin to the screen. Three small pieces stand in for the whole six app download stack this guide used to describe.
The honest trade off, before you commit This route rents rather than owns. The day the TorBox subscription lapses, or the source your feed points at goes down, your library becomes thousands of placeholder cards with nothing behind them, and there is no local copy to fall back on. The download route was slow and fiddly, but what it produced sat on your own disk and worked forever with no account attached to it. TorBox is a few dollars a month, so this is not an expensive habit, but it is a running one. Neither route is wrong; this build deliberately picks convenience and a library that fills itself, and keeps open the option of pinning a small handful of true favourites to real disk later so they survive an outage.
Check this first: your Jellyfin version Gelato needs Jellyfin 10.11 or newer to install at all. Before anything else, open Jellyfin, go to Dashboard, then About, and read the version number. If it is 10.11 or higher you are ready. If it is older, updating Jellyfin is the first job, and worth a snapshot of its container first out of the habit from the ops section. This one check decides everything downstream, so it comes before any account is created or any container is touched.

Where each piece actually lives

Understand this: only one of the three runs on your server It is worth being clear about where each piece sits, because it is less work than the old stack, not more. TorBox is simply an account on someone else's servers, so there is nothing to install for it at all. Gelato installs inside Jellyfin itself, as a plugin, from Jellyfin's own Dashboard, so it needs no container of its own either. The only piece that runs on your own machine is AIOStreams, and it runs as a Docker container. Docker is a second layer of containers that lives inside one of your Proxmox containers: rather than giving every small app its own full Proxmox container, you build one Linux container, install Docker in it, and then run app after app inside that as self contained packages called container images, each described in a single plain text recipe file. That means one Proxmox container built once, and every future app after this one is a few lines of text in the same file.

Step A, confirm your Jellyfin version

  1. Open Jellyfin in a browser, click the gear icon in the top right to reach the Dashboard, then choose About in the left menu. Read the version number at the top.
    You'll see: a version like 10.11.x. Anything 10.11 or higher is ready. If it is lower, Gelato will not appear as installable at all later, so update Jellyfin before going any further, and take a snapshot of its container first out of the habit from the ops section.

Step B, get your TorBox API token

  1. Create an account at torbox.app and pick a plan. This is the paid engine that makes playback instant, and it is the only thing in this section that costs money.
  2. Once signed in, open Settings, find the API section, and copy the API token. Paste it straight into your notes file.
    Treat this one as a secret, not as config: the token is not a password you type at a login box, it is a key that grants full access to a paid account to whoever holds it. It goes into your notes file, and from there it is pasted directly into the one screen that needs it. Not into a chat window, not into a screenshot, not into a message to someone helping you. If it ever does leak, TorBox lets you regenerate it on that same page, which instantly invalidates the old one; that is the right move and it costs you nothing but re-pasting it.

Step C, build the container that Docker runs in

From the Proxmox host Shell, the same place every other container was created:

bash -c "$(curl -fsSL https://raw.githubusercontent.com/community-scripts/ProxmoxVE/main/ct/docker.sh)"
  1. Choose Advanced settings when it asks, and give it 2 cores, 2GB memory and 8GB disk.
  2. The script then asks three questions in a row. Answer y to Portainer, and n to the Portainer Agent and to exposing the Docker TCP socket.
    What you just agreed to: Portainer is a web page for looking at Docker, reached at <its-address>:9443. Everything you run still gets defined in a recipe file you wrote, and Portainer is simply a window onto it where you can see what is running, read an app's logs and restart something without opening a shell. Worth having, as long as you keep defining things in the file rather than clicking them into existence in the window, because anything created by clicking exists nowhere in writing and cannot be rebuilt from memory later.
    Why the other two are no: the Agent is for a Portainer running on some other machine reaching in to manage this one, which is why the script only offers it if you declined Portainer itself; you have no such machine. The TCP socket is labelled insecure by the script for good reason: it opens control of Docker to the network with no password whatsoever, so anything on your network could start, stop or replace any app in this container. Answer n.
  3. Docker Compose, the recipe-file tool the rest of this section relies on, is installed as standard and is not one of the questions. The version check at the end of this step confirms it.
  4. When the script finishes it prints the new container's ID and address. Write both into your notes file.
    Why the address matters more here than usual: AIOStreams writes its own address into every link it hands out, including the one link Gelato needs. If you do not know the address before you configure it, you will configure it wrong and have to redo it.
  5. Set a DHCP reservation for it in your router, same habit as every other container, so the address it just told you never changes underneath it.
  6. Enter the container from the host and confirm Docker is actually running: pct enter <its-id> docker --version docker compose version
    A new one of the pct family: in the storage section you used pct exec to fire a single command into a container from outside it. pct enter is the other half: instead of shouting one instruction through the door, you walk in and stay. Your prompt changes to that container's name, and from then on everything you type happens inside it until you type exit. Everything in Step D is typed in here, not on the host, and mixing the two up is the single easiest way to end up with files in the wrong machine.
    You'll see: two version lines, one for Docker and one for Compose. If either says "command not found", the script did not finish; re-run it rather than trying to patch it by hand.

Step D, deploy AIOStreams

Everything in this step is typed inside the Docker container you just walked into, not on the Proxmox host. Make a home for it first:

mkdir -p /opt/aiostreams cd /opt/aiostreams
Why here, and what the -p is doing: /opt is Linux's conventional drawer for software that did not come from the package manager you met in the first Linux section, so hand-built things like this live there by custom rather than by rule. mkdir makes a folder and -p tells it to create any missing parent folders on the way rather than complaining, which also makes it harmless to run twice. A trailing letter or word after a command with a dash in front of it is called a flag, and it modifies how that command behaves; you have already used several without them being named.
  1. Confirm the container's own address, because you are about to write it into a file: hostname -I
    You'll see: one address, for example 192.168.1.193. That is the address the rest of this step uses.
  2. Generate the key AIOStreams uses to scramble its saved settings: openssl rand -hex 32
    What you just ran: OpenSSL is the standard toolkit every Linux machine carries for encryption work, and it is already installed. rand asks it for random data, 32 asks for 32 bytes of it, and -hex asks for that written out in hexadecimal, a way of writing numbers using sixteen digits (0 to 9, then a to f) instead of ten, which is how computers' raw data is normally shown in text. Each byte becomes two characters, which is why 32 bytes prints as 64 characters. Randomness is the entire point: a key you invented yourself would be guessable, and this one is not.
    What "encrypt" means here, plainly: AIOStreams stores your settings scrambled rather than in readable text, and this key is the only thing that unscrambles them. It is not a password you will ever be asked to type. It is more like the cut of a physical key: the lock does not check who you are, it only fits one shape.
    Copy this into your notes now, and never change it afterwards. Changing it later does not reset anything, it makes every existing setting permanently unreadable, including the link Jellyfin will be relying on. There is no recovery from that beyond setting the whole thing up again from scratch.
  3. Create the settings file, using the same editor you used for fstab back in the storage section: nano .env

    Type in these three lines, swapping in your own address and the key you just generated:

    BASE_URL=http://192.168.1.193:3000 SECRET_KEY=<the 64 characters openssl printed> DATABASE_URI=sqlite://./data/db.sqlite

    Save with Ctrl+O, Enter, then exit with Ctrl+X.

    The name really is just a dot: a filename beginning with a dot is hidden in Linux, which means a plain ls will not show it and you may think the file never saved. ls -a shows everything including hidden files. Nothing is secured by being hidden, it is only out of the way; the convention exists so config files do not clutter a folder listing. env is short for environment, the set of named values a program can read when it starts.
    What each line does: BASE_URL is the return address AIOStreams stamps onto every link it produces, which is why it needs all three parts, the http://, the address and the port, exactly as you type an address into a browser. SECRET_KEY is the key from the previous step. DATABASE_URI says where to keep its records; SQLite is a database that is nothing more than a single file sitting on disk rather than a separate service you have to run and look after, which is the right size for one household.
    Why a separate file at all: these could be written straight into the recipe file below, but they are not, and this split is the standard way software handles it. The recipe file describes how the app runs and is safe to share or publish; the .env file holds the parts that grant access and is never shared. It is the same config-versus-secrets distinction from the prep section, now enforced by two different files rather than by memory, and it is why almost every real project's ignore list starts with .env.
  4. Create the recipe file beside it: nano compose.yaml

    Type in exactly this. The indentation is not decoration, so keep the spacing as shown:

    services: aiostreams: image: ghcr.io/viren070/aiostreams:latest container_name: aiostreams restart: unless-stopped ports: - 3000:3000 env_file: - .env volumes: - ./data:/app/data

    Save and exit the same way.

    Why the spacing matters: this file is written in YAML, a plain text format built around indentation. Where most formats use brackets to show what belongs inside what, YAML uses how far in a line starts, the way an indented list in a document shows sub-points belonging to the point above. So image being indented under aiostreams is what makes it a setting of aiostreams. Get the spacing wrong and the file is not merely untidy, it means something different or refuses to load. Spaces only, never tab characters.
    Reading it line by line: services lists the apps this file describes, and aiostreams is the only one for now, which is exactly how you add a second app later, as another block beneath it. image names which prebuilt app package to fetch and from where; a container image is a ready-made, self contained copy of an app and everything it needs, published for anyone to download, which is why there is nothing to install by hand. restart: unless-stopped means it comes back on its own after a reboot or a crash, unless you deliberately stopped it. env_file pulls in the .env you just wrote.
    The two lines with a colon in the middle are the same idea you already met: in the storage section you opened a doorway from the host into the Jellyfin container, so a folder on one side appeared at a different path on the other. ports and volumes do exactly that for Docker, and both read outside on the left, inside on the right. 3000:3000 means port 3000 on the container is a doorway to port 3000 inside the app, which is how anything else on your network reaches it. ./data:/app/data means the folder data sitting beside this file (the ./ is shorthand for "right here") appears as /app/data inside the app. That second one is what keeps your settings when the app itself is thrown away and rebuilt, which is the normal way apps get updated here.
  5. Start it: docker compose up -d docker ps
    What the two commands are: docker compose up reads the recipe file in the folder you are standing in and makes reality match it, downloading anything missing and starting what is not running. -d is short for detached, meaning it hands your prompt back and lets the app keep running in the background instead of tying up your shell until you close it. docker ps lists what is currently running; ps is an old Unix name for process status, and you will meet it on its own in other contexts.
    You'll see: a few lines of the image downloading the first time, which can take a minute, then a line in docker ps showing aiostreams with a status beginning Up. If it is missing, docker compose logs prints what the app said as it tried to start, and a mistyped .env or a misaligned YAML line accounts for nearly all first attempts.

Step E, configure AIOStreams and get the one link out of it

  1. On any computer on your network, open http://<its-address>:3000/stremio/configure, using the address hostname -I gave you.
    The part after the port is a path: an address gets you to the machine and the port gets you to the right app on it, but many apps then keep different pages at different names underneath, written with slashes, exactly like folders. Visiting the bare address here lands somewhere unhelpful; the settings page lives at /stremio/configure and nowhere else. This is a normal thing for apps to do and you will meet it again.
    You'll see: AIOStreams' configuration page.
  2. Get your bearings first. Down the left of this page is a sidebar with six entries: Services, Addons, Filters, Sorting, Formatter and Save & Install. You need five of them, in that order, and the sixth is for tuning later.
    What the six are for: Services is who fetches the video, Addons is where titles and streams are looked up, Filters is which results you refuse outright, Sorting is which of the survivors comes first, and Save & Install is how you get the result out. Formatter only changes how results are labelled on screen, so that is the one you can leave alone.
    Why Sorting is not optional here, even though it sounds like decoration: in the usual way of using a setup like this, a person is handed a list of twenty results and picks one by eye, so the order is a convenience. Jellyfin never shows you that list. It takes the first result and plays it, and that is the whole of its decision-making. So on this setup, Filters and Sorting together are the choice you would otherwise have made by hand, and every result you fail to refuse or fail to rank is a result that can end up on your television.
  3. Open Services, find TorBox in the list, and click the cogwheel at the end of its row to open its settings. Paste in the API token from Step B, then close that panel.
    Why a whole list of them: AIOStreams supports many debrid providers and you are only using one. If you ever add a second, the order of this list is the order it prefers them in.
  4. Open Addons, then the Marketplace tab inside it. Search for TMDB and click Configure. Before you install it, change two things on that screen. In the Resources box, make sure catalog and meta are both selected. Then find the switch called Provide IMDB IDs and turn it on. Now click Install. Then search for Comet, configure it, leave its options alone, and install that too. Finally search for StremThru Torz and install it, and then search for AnimeTosho and install that one too.
    "Install" is a misleading word here: nothing is downloaded onto your machine and nothing new starts running. It means adding that source to your own personal blend, which is the entire job AIOStreams does. Think of it as ticking an ingredient rather than installing a program.
    Why more than one of them: they answer different questions. TMDB is a large public film and television database, free to use, and it supplies the titles, posters, years and descriptions, so it knows that a programme exists. The other three go looking for where a copy can actually be fetched from. With only the first, you end up with a beautiful library full of titles that will not play.
    Why three sources of streams and not one: Comet and StremThru Torz do the same job over different piles, so having both simply widens the net. AnimeTosho is there for a narrower and much less obvious reason. It covers anime only, and unlike the other two it is a source AIOStreams operates itself rather than a separate service it forwards your question to. That distinction sounds academic and it is the difference between a large part of an anime library playing and not playing, for a reason covered at the end of Step G. None of the three needs an account or costs anything, and all three fetch through the TorBox token you entered a moment ago.
    Why those two settings matter more than they look: catalog and meta are two separate jobs that people assume are one. Catalog supplies the browsing rows, the wall of posters under headings like Popular and Trending. Meta answers a much more specific question: tell me everything about this one programme, including how many seasons it has and which episodes are in each. Jellyfin cannot lay out a programme it has never been told the shape of, so without meta you get a library that looks perfect from a distance and has no working structure underneath.
    Why an id switch decides whether any of it works: every part of this chain refers to a programme by its IMDb id, the code beginning tt that you see in an IMDb web address. It is the one name everything agrees on. TMDB, being a different database, files things under its own numbering instead. Provide IMDB IDs tells it to answer questions asked the tt way as well as its own. Leave it off and requests arrive in a language it does not answer to, and you get back nothing at all rather than an error saying so, which is by far the harder kind of fault to notice.
    You'll see: all four listed under the Addons tab with a small tag each showing what they provide. TMDB should show that it provides catalog and meta; the other three should each show stream.
  5. Open Filters and scroll down to the Size section. On the Global tab you get three separate sliders, each with its own minimum and maximum box: Movies, Series and Anime Series. Leave all three minimums alone and set the maximums to about 20GB for movies, 5GB for series and 5GB for anime series. There is a per-resolution version of the same three sliders underneath; ignore it for now, the global ones are enough.
    Why you are deliberately refusing the biggest files: the sources behind this setup include remuxes, which are untouched rips straight from a disc with nothing compressed at all. A single film can be 60GB or 80GB. Nothing in your house benefits from that. Your television cannot show more detail than a good 15GB copy already contains, but every device between here and the screen has to move all 80GB of it in real time, and that is where stuttering comes from. Refusing them at this stage is one of the highest-value settings in this entire guide, and it costs you picture quality you would need a trained eye and a much larger television to notice.
    Why anime gets a slider of its own: an anime episode is usually about half the length of a drama episode, so the same number means something quite different depending on which you are watching, and the copies that circulate are often untouched disc rips at sizes you would normally expect from a feature film. With one number for everything you would be forced to choose: set it high and let those through, or set it low and start refusing ordinary television alongside them. The page itself tells you that where both could apply, the anime number is the one that counts, so if you watch any anime at all this box is not optional.
    What the number is actually compared against, because the obvious guess is wrong: a lot of results are bundles holding a whole season at once, and a season bundle can easily be 40GB. It looks like a 5GB limit would throw every one of those away. It doesn't. The limit is measured against the single episode being handed to you out of the bundle, not the bundle's total. The total is recorded separately, under a different name, and never gets compared to these numbers at all. So a 40GB season made of 1.4GB episodes is judged as 1.4GB and comes through untouched. The one exception is a result nobody has fetched before, where no particular episode has been picked out yet and the bundle's total is the only figure known, and those are the slow results you would be skipping past anyway.
    You'll see: nothing dramatic. This setting shows its worth later, as the absence of a problem rather than the presence of a feature.
  6. Still in Filters, find the Generic Stream Attributes group in the sidebar and open Encode. Each attribute here gives you four boxes, and the only one you want is Excluded Encodes: put AV1 in it. Then open Visual Tag just below, and in Excluded Visual Tags put DV Only. Leave the other boxes empty.
    What an "encode" is: video has to be squeezed down before it can be sent anywhere, and there are competing methods for doing the squeezing. Each one is a different puzzle, and a device can only unwrap the puzzles it was built to unwrap. AVC is the old one and everything on earth can play it. HEVC is the newer one and every screen you own handles it. AV1 is newer still, and while it is genuinely the cleverest of the three, most televisions and older phones cannot decode it at all, which sends the file straight back to the server to be rebuilt. You are refusing it not because it is worse but because it is the one thing in this list your household cannot open.
    Why DV Only and not DV: Dolby Vision is a brighter, richer colour format. Some files carry it as an extra layer sitting on top of an ordinary version, so a screen that doesn't understand it simply ignores the layer and shows the ordinary picture. Other files carry it and nothing else, and on a screen that doesn't understand it those play in lurid green and purple, which is the single most alarming-looking fault in home video and looks like a broken server. This page separates the two cases for you, and DV Only means exactly the second one. Excluding it removes the files that break and keeps every file that would have looked fine, which is why this is a better setting than refusing Dolby Vision outright.
    You'll see: your chosen terms sitting as small tags inside those two boxes. Nothing else changes on screen.
  7. Still in Filters, find Cache in the sidebar and turn on Exclude Uncached Streams. A few boxes appear underneath it for applying the rule to only certain addons or services; leave every one of them empty, which means it applies to all of them.
    What cached means, because the word is doing a lot of work: your debrid service is one enormous shared shelf. When somebody, anybody, has already asked for a particular copy of something, it is sitting on that shelf ready to hand over, and it starts playing in a second or two. That is cached. When nobody has ever asked for that exact copy, asking for it does not fetch it from a warehouse. It starts a fresh download from whoever happens to be sharing that file at that moment, which might be dozens of people or might be nobody at all. That is uncached.
    Why an uncached result is a dead end rather than a slow one: because Jellyfin plays the first result without showing it to you, you never get the chance to look at one and think "that will take an hour, I'll take the other one". You press play and get a purple screen saying the file is being downloaded to your debrid, try again later. If a few people are sharing it, later means a few minutes. If nobody is, it means never, and nothing tells you which of the two you are in. Refusing them outright turns an unanswerable wait into an honest "no stream found", which is the far better failure because you can see it and act on it.
    What you give up, stated plainly: anything obscure enough that nobody has fetched it before will now report no streams instead of offering to fetch it. That is a real loss and it is worth it, because on this setup the offer was rarely one you could accept anyway. If you ever hit something you badly want and cannot get, you can come back and switch this off for one evening.
    You'll see: the switch on, and the extra boxes below it empty.
  8. Open Sorting, the next entry in the sidebar, and stay on the Global tab. There is a box for adding criteria and it starts empty. Add three, in this order: Cached, then Seeders, then Size. Each one drops in as a row you can drag, with a small arrow button on the right showing which way round it goes. All three want to be pointing the way they arrive, which is largest-first, so add them and change nothing else.
    What a list of criteria actually means: it is a set of tie-breakers read top to bottom, the way you would sort a pile of papers by date and then, for two on the same date, by name. Cached first puts the ones that start instantly above the rest. Seeders next means that among equals, prefer the copy the most people are sharing, which is a good proxy for the copy least likely to stall. Size last means that among those, take the biggest, and since you already capped the maximum in the Size filter, biggest here means the best-looking copy that is still under your ceiling rather than an eighty gigabyte monster.
    Why Cached appears in both places: the filter throws uncached results away and the sort ranks what is left, so with the filter on, the Cached line is doing nothing today. Leave it there anyway. The day you switch the filter off to chase something obscure, that line is what stops an uncached result jumping in front of a perfectly good cached one, and a setting you have to remember to add back is a setting you will forget.
    You'll see: three rows under the Global tab in that order. The other tabs, for movies, series and anime separately, stay empty and fall back to this one.
  9. Open Save & Install, the last entry in the sidebar. Under Save Configuration, set a password and click Save.
    What that password is for: it locks this configuration, not the app. Anyone on your network who opens this address could otherwise change which services and sources you use, or read the token you pasted in earlier. It also comes back out with the UUID shown just above it, and those two together are what let you return and edit this configuration later, so both belong in your notes file.
  10. Under Installation Options, find Direct Manifest URL on the right and copy it. Paste it into your notes file. That address is the manifest, and it is the one thing Step F needs. Ignore the Install to Stremio buttons beside it; those are for people using Stremio as their player rather than Jellyfin.
    What a manifest is: one web address that describes everything this addon can do and where to ask for it, the addon's own contents page. Every choice you just made travels inside it, which is why Jellyfin only ever needs this single link and never needs to know about TorBox, TMDB or Comet by name.
    Treat this link as a credential, not an address. Your configuration's identifier is part of the URL itself, so anyone holding it can use your setup and therefore your paid TorBox access. It goes in your notes file and gets pasted into Jellyfin, and nowhere else. If it ever gets out, come back here, save with a new password, and the old link stops being useful.

Step F, install Gelato inside Jellyfin

  1. In Jellyfin, go to Dashboard, then Plugins, then the Repositories tab, and click the + to add one. Give it any name you like, and for the URL enter exactly: https://raw.githubusercontent.com/lostb1t/Gelato/refs/heads/gh-pages/repository.json
    What you just added: a plugin repository is a catalogue address, not the plugin itself. Jellyfin ships knowing about one official catalogue; adding a second one just tells it about another shelf it is allowed to browse. Nothing is installed by this step.
  2. Go to the Catalogue tab, find Gelato in the list, and install it. When Jellyfin asks you to restart, restart it.
    One thing to avoid back in AIOStreams: Gelato's authors specifically warn against the Debridio flavours of the TMDB addon, which appear alongside the plain one when you search. Use The Movie Database, the one whose id reads tmdb-addon, which is what Step E told you to pick.
    You'll see: Gelato appear under My Plugins with a status of Active after the restart. If it never appears in the catalogue at all, the version check in Step A is the first thing to re-read.
  3. Open Gelato's settings. Once the plugin is installed it gets its own Gelato entry in the Dashboard sidebar, under the Plugins group, which is the quickest way in. Paste the manifest link from Step E into AIOStreams URL. Then change Movies Path and Series Path, which arrive pointing at /tmp/gelato/..., to these instead, and save: /media/gelato/movies /media/gelato/series
    Do not leave the defaults. /tmp is Linux's scratch drawer, meant for things that only need to exist while the machine is running, and it is emptied on every reboot. Left as they are, your entire library disappears the next time that container restarts. /media is the doorway onto your big drive that you opened in the storage section, so the two paths above survive both reboots and the container being rebuilt.
    Why not point these at the folder holding films you already own: these two folders are how Gelato marks its own territory, and Jellyfin uses them to tell rented titles apart from owned ones. Point them at your real folders and that line disappears, which is exactly the line you want to be able to see the day a subscription lapses. Keep them apart. Write both paths into your notes file, because the next step points Jellyfin at these same two and they have to agree exactly.
    Keep films and series in separate paths. They arrive that way by default, so this is only a warning against tidying them into one. If a single folder holds both, Gelato does not throw an error. It fills the library anyway and the result looks half right, with series appearing as single films, episodes missing, or artwork attached to the wrong thing. Because there is no error message to search for, this is worth getting right on the first pass rather than debugging afterwards.
  4. Stay on the same settings page and scroll down to Importer. It lists every catalogue your feed can offer, each with a Name, a Type of movie or series, an Enabled tick box, a Collection tick box and a Max items number. They all arrive switched off. Tick Enabled on the ones you want, then save.
    Nothing at all is imported until you do this. The list starts empty of ticks, and the import task treats that as a full and valid instruction: fetch nothing. It runs, reports success, finishes in under a second and leaves you with two empty libraries and no error anywhere. If you take one thing from this step, it is that a successful import and an empty library usually means nothing is ticked here.
    What to tick to begin with: Trending and Popular in both movie and series flavours are the sensible start, because they are the closest thing to a general "what is worth watching" shelf. Every catalogue you add is more rows in the database and a longer import, so switch on a few, see what the library looks like, and come back for more rather than ticking everything on the first pass.
    What Max items does: it caps how many titles that one catalogue contributes, and it starts at 100. That is a deliberate brake rather than a limitation to work around. A hundred titles from each of several catalogues is already a large library, and raising it multiplies both the import time and the amount Jellyfin has to sift through every time it draws a screen.
    What the Collection tick box does: it makes Jellyfin build a collection, its word for a named shelf you can open like a folder, holding exactly that catalogue's titles. The titles still sit in the ordinary library alongside everything else, so this is a second way in rather than a separation. It is useful when a catalogue is a coherent theme worth browsing on its own.

Step G, give Gelato its libraries, then fill them

  1. In Jellyfin, go to Dashboard, then Libraries, then Add Media Library. Create one of type Movies pointed at the Movies Path from your notes, and a second of type Shows pointed at the Series Path.
    Why two libraries and not one: Jellyfin treats a library's type as a promise about what is inside it, and it reads a film and an episode very differently. This is the same reason the paths are separate, enforced a second time at the Jellyfin end.
  2. On the Shows library only, scroll down and you will find not one list of metadata downloaders but three, each labelled with a bracket: Metadata downloaders (TV Programmes), Metadata downloaders (Series) and Metadata downloaders (Episodes). In each of the three, tick Gelato and drag it to the top. Then save.
    Why there are three of them: a shows library holds three different levels of thing. The programme, the seasons inside it, and the episodes inside those. Jellyfin looks each level up separately, so each level gets its own ordered list of who to ask. Think of a filing cabinet where the drawer, the folders in the drawer and the pages in the folders each have their own librarian.
    Why the order matters: each list is a queue, not a committee. Jellyfin asks the first entry and takes its answer, and the ones below only fill in what is still blank. The ordinary downloaders describe episodes that exist as real files on disk, and this library has none, so if one of them answers first your series show up as empty shells. Gelato has to be asked first for the seasons and episodes to appear at all.
    Gelato is listed in the Movies library too. Leave it unticked there. A plugin registers once and Jellyfin then offers it everywhere, whether or not it has anything useful to say. Gelato's only skill here is inventing seasons and episodes that have no file behind them, and a film has no inside, so there is nothing for it to do. The downloaders already ticked in that library are the right ones for films.
  3. Go to Dashboard and look down the left sidebar to the Advanced group near the bottom, where you will find Scheduled Tasks. Open it, find Gelato's catalog import task, and run it.
    Nothing appears without this: creating the libraries only tells Jellyfin where to look. This task is what actually goes and fetches the catalogue through AIOStreams and writes every title it finds into Jellyfin's own database, filed under those two paths. A scheduled task in Jellyfin is a job it runs on a timer, and every one of them can also be triggered by hand, which is what you are doing here.
    You'll see: the task running with a progress indicator, then the two libraries filling with title cards over the next few minutes, while the disk barely moves.
    Look in those folders and they will still be almost empty. Each holds a single small file called stub.txt, and that is correct. Gelato does not write a file per title. It puts each title straight into Jellyfin's catalogue as a database entry, and the one stub.txt exists only to give Jellyfin something real to find so it agrees to scan the folder at all. Leave that file alone. An almost empty folder next to a full library is the setup working exactly as intended.
  4. Stay on that page and look at the rest of the Gelato group. Alongside the import sit Sync series trees and Sync release dates. Both already run by themselves, at startup and once a day, so there is nothing to schedule. Run Sync series trees once by hand now, so you have seen it work and know where it lives.
    Why a programme that is still being made needs a job of its own: the import wrote down the programmes as they were on the day it ran. A finished series never changes again, but one that is still airing grows underneath you: a new season arrives at the source weeks later, and nothing goes back to look for it unless something is told to. That is this task's entire purpose. It is also why a show can sit in your library quite happily for months and then sprout a new season that refuses to play while every older episode is fine.
    A red Missing label is not the fault it looks like: open any episode's media information and you will often see the word Missing in red, including on episodes that play perfectly well. In an ordinary Jellyfin library that word means a file you expected to be on the disk is not there. Here there are no files at all, so it means something much milder: no stream has been chosen for this episode yet. Gelato only goes looking for one at the moment you press play, so until you have played it, an episode honestly does have nothing attached. Judge an episode by whether it plays, not by that label, and if you are ever unsure, look at the label on an episode you know works and compare.
    What the release dates one is for: it stamps each title with the date it actually became available, which is what Gelato uses if you ever switch on its filter for unreleased items. Harmless to run, and worth running now so the dates are already there if you turn that filter on later.
    Two entries in that group are destructive and one of them is called purge. They delete Gelato's items or its cached streams and exist for starting over from nothing. Neither has any part in setting this up. Read the name before clicking anything in this group.
If one season refuses to play while everything older is fine Run Sync series trees first, since a new season that is not there at all is usually just that task not having run since the season appeared. If the episodes are listed but will not play, open the programme, use the three dots, choose Refresh metadata with Replace all metadata, and let it rebuild that one show rather than the whole library.

If it still will not play, the thing to check is the numbering, and it helps to know exactly what Gelato does when you press play. It takes three pieces of information: the programme's IMDb id, which you can see under Edit metadata, plus the season number and the episode number shown on that episode. It glues them together into a single request and asks AIOStreams for anything matching. If the id is blank it has nothing to ask with. If the numbers do not mean the same thing at the far end, it asks a perfectly well formed question about an episode that, as far as the sources are concerned, does not exist, and gets an empty answer back with no error.

That second case is where anime comes unstuck, and it is worth understanding rather than memorising. Western programmes are counted the same way everywhere: series three, episode one. A lot of anime is counted straight through instead, so the first episode of the fourth season is episode sixty-seven of one long run. Both are legitimate. The trouble starts because your metadata source picks one of the two and the people naming the files picked the other, so season one episode sixty-seven and season four episode one are the same programme under two names with nothing joining them up. The tell is very specific: everything up to a certain episode plays, and everything after it does not.

There is no metadata source that gets this right for every programme, so the fix is not to keep swapping them until one fits. It is to have at least one stream source that works the numbering out for itself, and that is the entire reason Step E has you install AnimeTosho alongside the others. Most addons are separate services that AIOStreams only forwards your question to, so a badly addressed question goes out and an empty answer comes back, which is why adding more of that kind never helps. AnimeTosho is one AIOStreams runs itself, so it can look the programme up first, recognise a series that is counted straight through, work out both ways of naming that episode and search for both. It then stops mattering which of the two your metadata happens to use. If you skipped it, go back and add it now, and restart Jellyfin afterwards for the reason given just below.
If you change your AIOStreams configuration later Any time you go back to AIOStreams and alter which services or addons it uses, restart Jellyfin afterwards. Gelato reads that configuration when it starts and does not notice it changing underneath, so without a restart you get the old behaviour and no error explaining why. Worth remembering, because the symptom looks like your new addon simply not working.

Step H, test one play

  1. Open Jellyfin in a browser on your computer rather than on a TV app, pick a film Gelato has filled in, and press play.
    You'll see: a few seconds of nothing while Gelato asks AIOStreams for a stream and AIOStreams resolves it through TorBox, then the film starts. Nothing is written to disk.
    Why a browser first: if something is wrong, a browser tells you plainly and lets you check Jellyfin's Dashboard logs in the next tab. A TV app tends to fail with a single unhelpful message, which turns a two minute fix into an evening.

Step I, keep it on direct play, now that the file lives somewhere else

Understand this: transcoding was expensive before, and it's worse now Back in the Jellyfin section you met the two ways a video can reach a screen: direct play, where the server hands the file over untouched, and transcoding, where the server rebuilds it on the fly because the app can't cope. That mattered then. It matters far more now, and it's worth understanding why rather than just being told.

When the file sat on your own drive, transcoding meant the server reading from a disk two feet away, which is about as fast and reliable as anything gets. Nothing on this build sits on a disk any more. The video lives on your debrid provider's servers, out on the internet, and arrives through your broadband connection.

That changes the maths in two ways. To rebuild a video on the fly the server has to read the source faster than it plays, so it's fighting to stay ahead over a connection it doesn't control. And the moment somebody skips forward, the server has to stop and ask for a chunk from the middle of a file it doesn't hold, wait for that request to travel out and come back, and only then resume. That pause is exactly the buffering people describe when they say seeking feels sluggish, and it doesn't happen at all during direct play, because the app is fetching its own data in a steady line and the server never gets involved.

So the size limit you set in Step E and the app you chose back in the Jellyfin section are not two separate bits of housekeeping. They are the same decision approached from both ends: keep the file small enough to move comfortably, and use an app capable enough that the server is never asked to touch it.
  1. Play something and, while it's playing, open Dashboard in Jellyfin and look at the active session. It tells you plainly whether the stream is direct playing or transcoding, and if it's transcoding it gives a reason in words.
    You'll see: ideally the words Direct playing. If instead you see Transcoding with a reason such as "the video codec is not supported", that reason is naming the app, not the file. The same file in a capable app plays untouched.
    Why this screen is worth knowing by heart: it turns a vague complaint ("it's laggy") into a specific fact you can act on. Nearly every media server problem people give up on is one they never checked here first.
  2. If it says transcoding and you were watching in a browser or the official mobile app, try the same title again in one of the apps named in the Jellyfin section, and check the Dashboard once more.
    Why the browser is the worst case: a web page is only allowed to play the small handful of formats the browser itself understands, so it refuses the most, which forces the server to work the hardest. It's a fine tool for testing, as Step H used it, and a poor one for actually watching.
Subtitles, and the trap inside them Subtitles come in three kinds and the differences are not cosmetic, so it is worth learning all three now rather than meeting them one confusing evening at a time.

Plain text subtitles are files ending .srt: words with timings and nothing else. Any app can draw those over the picture for free, and they are the easy case.

Image subtitles (PGS and VobSub, very common inside .mkv rips taken from discs) are not words at all. They are tiny pictures of words. There is no way to draw a picture as text, so it has to be painted onto the video itself, and painting anything onto the video means rebuilding every frame, which is a transcode.

Styled text subtitles (ASS and SSA, which almost every anime release uses) sit awkwardly between the two. They are real text, so they are not the picture problem, but they also carry their own fonts, positions, colours and sometimes animation, because fansubbers use them to label signs and shop fronts in the scene. Drawing them properly needs a small typesetting engine, and an app either has one or it doesn't. If it doesn't, the server has to paint them on, and you are back to a transcode even though the file itself was small and well behaved.

That third case is why "just pick smaller files" is not the whole answer, and it is the one place where the tidy story in this section has a genuine edge to it. The apps named in the Jellyfin section all carry that typesetting engine, so they handle image subtitles and styled subtitles alike without asking the server to touch anything. Televisions are the exception, as they were before: on a Samsung or LG set, a heavily styled anime track may still force the server to burn the subtitles in. If that happens the Dashboard will say so in words, and the honest fix is to watch that particular thing on a phone or a computer rather than to fight the television.
Only tear the old stack down once this one plays If you are moving here from the old download stack rather than starting fresh, resist removing it until a title has actually streamed through Gelato at least once. The moment to retire Sonarr, Radarr, Prowlarr, qBittorrent, gluetun and Jellyseerr is after the new route is proven, not before, so the household is never left with a library that neither downloads nor streams. Once Gelato plays cleanly, the old docker compose down on the arr stack is safe to run.
Recap
  • This route keeps almost nothing on disk. It fills the library with catalogue entries rather than files, and fetches the real video on demand when someone presses play, the shop window rather than the warehouse.
  • Three pieces do it: TorBox (the paid engine that makes playback instant), AIOStreams (the adapter that gathers sources into one feed, run as a Docker container), and the Gelato plugin inside Jellyfin (which writes the catalogue entries and resolves a stream on play).
  • The trade is convenience for ownership: it fills itself and never stalls, but it rents from an outside service, so nothing plays if that service or subscription goes away. Gelato needs Jellyfin 10.11 or newer.
  • Because the video now arrives over the internet rather than off a local disk, transcoding hurts far more than it used to, and skipping forward is where you feel it first.
  • Two ideas prevent nearly all of it: refuse the files that cause trouble in AIOStreams, which means the size limits plus the two attribute exclusions, and use a capable app so the server is never asked to rebuild anything. Jellyfin's Dashboard tells you which of the two is happening at any moment.
  • The size limits are compared against the episode you are handed, not the season bundle it came out of, so a low series limit does not quietly cost you season packs.
Check yourself

Q1. Your library shows thousands of films but the disk is nearly empty. Where is the actual video for a film you have not watched yet?

Nowhere on your disk. Each title is only an entry in Jellyfin's catalogue until you press play, at which point Gelato fetches the real stream on demand from your debrid engine through AIOStreams. Nothing is stored unless you deliberately pin it later.

Q2. What is the one thing that stops working if your TorBox subscription lapses, and why is that different from the old download setup?

Playback stops entirely, because the debrid engine that actually serves the video is gone, leaving only empty placeholder cards. The old download setup kept real files on your own disk, so they would keep playing regardless of any subscription.

Q3. Why does transcoding cause more trouble here than it would if your films were sitting on the drive in the machine?

Because the source is out on the internet rather than two feet away. To rebuild the video on the fly the server has to read it faster than it plays over a connection it doesn't control, and every time somebody skips forward it has to request a chunk from the middle of a file it doesn't hold and wait for that round trip.

Q4. Somebody turns on subtitles and a film that was playing fine starts stuttering. What's happening?

The subtitle track is almost certainly image-based (PGS or VobSub), which cannot be drawn as text and has to be painted onto the video itself. That means rebuilding every frame, which is a transcode. A capable app renders those itself instead of asking the server to do it. A heavily styled ASS track can cause the same thing on a television, for a different reason: it is real text, but it needs a typesetting engine the television doesn't have.

Q5. You set a 5GB limit on series. A season bundle weighing 40GB contains the episode you want. Does your limit throw it away?

No. The limit is compared against the single episode being handed to you, not the bundle it came from, so an episode of 1.4GB passes regardless of what the whole season weighs. The bundle's total is recorded separately and is never checked against that number.

Q6. Why refuse files tagged "DV Only" while happily accepting other Dolby Vision files?

Because most Dolby Vision files carry it as an extra layer on top of an ordinary picture, so a screen that doesn't understand it just ignores the layer and looks normal. "DV Only" means the file has nothing underneath, and on a screen that doesn't understand it the picture comes out green and purple. Refusing only that case removes the files that break and keeps every file that would have been fine.

You'll meet this again The rent versus own decision you just made is the same one every organisation makes between streaming or a content delivery network and local storage, and between renting cloud capacity and buying your own hardware, an explicit cost and reliability trade in AZ-900's pricing and capex versus opex topics. Extending an application by dropping in a plugin, and wiring services together by handing one an API token for another, are both everyday patterns in real software integration. And Docker with a docker-compose.yml is still exactly the infrastructure as code idea behind Azure Container Instances and Kubernetes at cloud scale, describing what should run in one file rather than clicking through installs by hand.

11.One front door for the family: a dashboard, a memorable address, and no ports

Right now, reaching anything means knowing its exact IP address and port, which is fine for you but not realistic for the rest of the household. This section fixes that with two small pieces working together: a dashboard that turns every service into a single clickable tile, and one memorable address for the whole family to type instead of any of them.

Understand this: the two separate jobs being solved here A dashboard solves "where do I click", one page with an icon per service, so nobody needs to remember or even see an IP or port, they just tap Jellyfin and land in Jellyfin. A memorable local DNS name solves "what do I type to get there in the first place", one easy word instead of a string of numbers. Together they mean a family member only ever needs to know one thing.

Step A, the dashboard itself

Create it the same way as everything else, run from the Proxmox host:

bash -c "$(curl -fsSL https://raw.githubusercontent.com/community-scripts/ProxmoxVE/main/ct/homepage.sh)"

Defaults: 2 cores, 4GB memory, 6GB disk, reached at <its-ip>:3000. Once it's up and working, set a DHCP reservation for it in your router, same habit as every other container.

Understand this: a dashboard built from a file, not a click This one doesn't have a page where you fill in tiles by hand. Everything about it, every tile, every icon, every live number it shows, is described in a small handful of plain text files sitting inside the container, and the app simply reads them and draws the page from whatever it finds. That's the same idea as the recipe file from the last section: the whole dashboard exists as something you can read, back up, and rebuild from a text file, rather than something that only exists because of clicks nobody wrote down.
  1. Enter the container and look at where its settings live: pct enter <its-id> ls /opt/homepage/config
    You'll see: a handful of files ending in .yaml, most importantly services.yaml, the one that lists your tiles. It starts out nearly empty, which is why the dashboard is blank the first time you visit it.
  2. Open the tile list: nano /opt/homepage/config/services.yaml

    Clear whatever is already in the file and type this in as a starting layout, swapping in your own containers' real addresses in place of the ones shown:

    - Media: - Jellyfin: icon: jellyfin.png href: http://192.168.1.60:8096 description: Watch something widget: type: jellyfin url: http://192.168.1.60:8096 key: <Jellyfin API key, see the next step> - Network: - Pi-hole: icon: pihole.png href: http://192.168.1.97/admin description: Ad blocking and DNS widget: type: pihole url: http://192.168.1.97 version: 6 key: <your Pi-hole password> - Infrastructure: - Portainer: icon: portainer.png href: https://192.168.1.193:9443 description: See what Docker is running - AIOStreams: icon: docker.png href: http://192.168.1.193:3000/stremio/configure description: Streaming source configuration

    Save with Ctrl+O, Enter, then exit with Ctrl+X. The dashboard notices the change and redraws itself within a few seconds, no restart needed.

    Reading the shape of it: the same indentation rules from the AIOStreams recipe file apply here, this is YAML again. The three names sitting furthest to the left, Media, Network, Infrastructure, are groups, nothing more than a heading drawn above the tiles listed under them. Each tile below needs at minimum an icon, an href (where clicking it takes you), and a description. The optional widget block is what turns a plain clickable tile into one that also shows a live number pulled from that service, which is why Portainer and AIOStreams above are left as plain tiles for now, each would need its own separately fetched key to go further, worth coming back for once the pattern below feels familiar.
    Where the icons come from: the app ships already knowing a large shared library of app icons by name alone, jellyfin.png and pihole.png among them, so typing the name is enough. Nothing to download or host yourself.
  3. Get Jellyfin's half of the widget working. In Jellyfin, go to Dashboard, then look down to the Advanced group and open API Keys. Click the +, and give it a name like homepage. Copy the key it generates straight into the key line under Jellyfin in the file above, and into your notes.
    What this key actually is: the same idea as the TorBox token from the last section, a credential rather than a password. This one lets the dashboard ask Jellyfin questions like "what's playing right now" without logging in as an actual person. Naming it something recognisable matters, since Jellyfin lists every key you've issued by name, and lets you revoke one individually the day it's no longer needed.
  4. Test it: visit <its-ip>:3000 again.
    You'll see: three named groups of tiles. Jellyfin and Pi-hole each show a live line of numbers beneath their name, Jellyfin's current stream count, Pi-hole's queries blocked today. Portainer and AIOStreams stay plain clickable tiles for now, exactly as expected.

Step B, one name for the whole house

Understand this: why Pi-hole is the right tool for this too Pi-hole is already the phone book the whole house uses to look up names. Adding your own entry to that phone book is exactly the same idea as it looking up bbc.co.uk, except this entry only exists inside your own house, nobody on the outside internet has ever heard of it, and it can point at whatever you like.
A genuine gotcha worth knowing before you pick names Browsers keep an internal list of endings they trust as real, .com, .org, and so on. Anything invented, like .home or .lan, isn't on that list, and modern browsers (Firefox especially) will quietly send an invented ending to a search engine instead of trying to visit it, purely as a safety precaution. The fix is simple: use a made-up name that still ends in a real, recognised TLD like .com. You never register or pay for it, Pi-hole simply answers for it entirely inside your own house before the request would ever reach the real internet, and because the ending looks legitimate, every browser trusts it and navigates straight there.

Worth picking a consistent pattern rather than a different style each time. This guide uses nadri<service>.com, so nadrihome.com for the dashboard, nadrijellyfin.com, nadripihole.com, and so on as you add more, swap in whatever prefix you like.

  1. In Pi-hole's admin page, go to Local DNS, then DNS Records.
  2. Add a new record: in the domain field enter nadrihome.com, and in the IP field enter just the bare IP address, Homepage's address on its own, nothing else typed alongside it. Click Add.
    Only the address goes in that box: no http://, no port number, no trailing slash. A DNS record can only ever answer "what address does this name mean", it has no way to carry a port or protocol alongside it, so anything extra typed in there gets rejected.
  3. On any device already using Pi-hole for DNS, open a browser and go to http://nadrihome.com:3000.
    You'll see: Homepage loads. Notice the port number still had to be typed, that's the one piece a plain DNS name can never remove on its own, which is exactly what Step C below finishes off.

Step C, dropping the port number too: a reverse proxy

Understand this: why the port can't be avoided without one more piece When a browser gets a name with no port typed after it, it silently assumes port 80 (or 443 for a locked https:// address). Homepage doesn't live on port 80, it lives on 3000, so typing the name alone lands nowhere until something is actually sitting on port 80 ready to answer. A reverse proxy is that something: a single doorway on the normal port that looks at which name was asked for, and quietly forwards the visitor on to whichever real container and port actually handles it, Homepage, Jellyfin, Pi-hole, whatever it's told to. Every name can then work with nothing typed after it at all.

Create it the same way as everything else, run from the Proxmox host:

bash -c "$(curl -fsSL https://raw.githubusercontent.com/community-scripts/ProxmoxVE/main/ct/nginxproxymanager.sh)"

Defaults: 2 cores, 2GB memory, 8GB disk. Its own admin page runs on port 81, reached at <its-ip>:81, that one port is the only exception you'll ever need to type, since it's how you manage the proxy itself, not one of the family's everyday addresses. On first visit it walks you straight into creating your own admin account, no default login to worry about.

  1. Inside Nginx Proxy Manager, go to Hosts, then Proxy Hosts, then Add Proxy Host.
  2. Under Domain Names, enter nadrihome.com. Under Forward Hostname / IP, enter Homepage's actual address. Under Forward Port, enter 3000. Save.
    What you just told it: "when someone asks for nadrihome.com, quietly walk them through to Homepage's real address on port 3000." The visitor never sees or types that port at all.
  3. Back in Pi-hole's Local DNS Records, edit the nadrihome.com record you made in Step B so its IP now points at the proxy's address instead of Homepage's own address directly.
    Why this changes: every name now needs to be pointed at the one doorway (the proxy), which then decides internally where each name actually goes. Pointing straight at Homepage again would skip the doorway and land you back needing the port.
  4. Repeat both steps, a Pi-hole record plus a matching Proxy Host entry, for each additional service, nadrijellyfin.com forwarding to Jellyfin's address on port 8096, nadripihole.com forwarding to Pi-hole's address on port 80, and so on, all sharing the one nadri<service>.com pattern.
  5. Test it: http://nadrihome.com, with nothing after it at all.
    You'll see: Homepage, no port typed anywhere. That's the whole chain working end to end, a name resolves to the proxy, and the proxy quietly finishes the journey.

Step D, when a service lives one level deeper: Pi-hole's /admin

Understand this: not every service greets you at its own front door Some services put their actual interface one level in, at a specific path, rather than right at the address itself. Pi-hole is exactly this: visit its address alone and you land on a mostly blank holding page, the real dashboard lives at /admin on top of that address. Typing nadripihole.com/admin every time works, but it defeats the point of a short, memorable address, so the fix is to teach the proxy to automatically take that extra step for you.

In Nginx Proxy Manager, open the Proxy Host you made for Pi-hole (nadripihole.com), and click into its Advanced tab. Paste this into the custom configuration box:

location = / { return 301 /admin; }

Save.

Reading it: this says "if someone arrives at exactly the bare address (/), send back a note telling their browser it's moved to /admin." The 301 is the standard code meaning "moved permanently", and getting one is what makes the browser automatically ask again at the new location, without you typing anything further.
  1. Test it: http://nadripihole.com, nothing typed after it.
    You'll see: the address bar itself updates to show /admin added on the end, and Pi-hole's actual login page loads, all without you typing it yourself.

The same trick applies to any future service that hides its real interface behind its own path rather than its own root, just swap /admin for whatever that service's actual path turns out to be.

Step E, make it yours: renaming tiles, custom icons, and using the cleaner links

Understand this: a tile's name is a label, not a connection The words on a Homepage tile are nothing more than a heading you wrote, Homepage never checks them against anything, so renaming one is purely cosmetic and cannot break the thing it's pointing at. What actually makes a tile work is the href underneath, and, if there is one, the widget block's own type, neither of which has anything to do with what the tile is called.
  1. Back in services.yaml, rename Jellyfin's entry to whatever you want your family to see, give it a different icon from the same shared library as before, and swap its href for the memorable address you just built: - Media: - Nadriflix: icon: netflix.png href: http://nadrijellyfin.com description: Watch something widget: type: jellyfin url: http://192.168.1.60:8096 key: <your Jellyfin API key>
    What actually changed, and what didn't: the name on the tile is simply whatever you write as that entry's own heading, Jellyfin never sees it and doesn't care, so calling it Nadriflix instead of Jellyfin changes nothing about how it works. The widget block underneath still says type: jellyfin, because that's the line telling Homepage which app's API to actually speak to, regardless of what the tile is named. Renaming the label and swapping the icon is pure decoration sitting on top of a connection that hasn't moved.
  2. Notice the two addresses in that block are different on purpose. href, the link the tile actually opens when clicked, now uses the memorable nadrijellyfin.com address built earlier in this section. The widget's own url, the one Homepage quietly asks in the background every so often for a live number, stays pointed straight at Jellyfin's real address rather than routed through the proxy.
    Why not send both through the nicer address: nothing stops you, the network path works either way. But the widget line runs constantly and automatically in the background, and every extra piece it depends on, here, going through the reverse proxy rather than straight to Jellyfin, is one more thing that could be down when it asks. The href only matters at the single moment someone actually clicks it, so that's the one place the friendlier look costs nothing to use.
    The same idea extends to your other tiles. Pi-hole's href can become http://nadripihole.com now that Step D's redirect sends it straight to its login page. Portainer and AIOStreams don't have a Pi-hole record or proxy entry set up anywhere in this guide, so leave those two on their raw addresses unless you go back and give each its own nadri<service>.com entry first.
You'll meet this again This is a small taste of what internal DNS and service discovery do inside real organisations at a much larger scale, and a reverse proxy is one of the single most common pieces of real infrastructure anywhere, the exact same job Azure's Application Gateway or a load balancer does in front of cloud services, just at home-lab scale. The redirect trick above is a plain example of an HTTP status code doing real work, the three-digit numbers (301, 404, 200 and so on) that every web request and response carries, worth recognising them as a concept you'll meet constantly from here on.
Recap

  • A local DNS record in Pi-hole gives the whole house one memorable name instead of an address. Ending it in a real, recognised TLD like .com keeps browsers from treating it as a search, even though it's never actually registered on the public internet. A DNS record can only ever hold a bare address, never a port or protocol.
  • A reverse proxy sits on the normal port and forwards each name on to its real container and port internally, which is what finally lets a name work with nothing typed after it.
  • A service that lives behind its own path, like Pi-hole's /admin, needs one extra rule in the proxy, a 301 redirect, so the bare address automatically continues on to the right place.

Check yourself

Q1. Why does a made-up name like nadrihome.home risk triggering a search instead of navigating, while nadrihome.com doesn't, even though neither is a real registered website?

Browsers only trust endings they recognise as real, registered TLDs, like .com. An invented ending like .home isn't on that list, so browsers assume it's probably a typo and search instead. Ending the made-up name in a real TLD keeps the browser's trust, even though Pi-hole is answering for it entirely locally and it was never actually registered.

Q2. Once the reverse proxy is in place, what does each Pi-hole DNS record need to point at, and why?

The proxy's own address, not each service's own address directly. The proxy is the one thing listening on the normal port and deciding where each name actually goes internally, so every name needs to be routed through it first.

Q3. Why does Pi-hole need an extra rule in the proxy that Homepage and Jellyfin don't?

Pi-hole's real dashboard lives one level in, at /admin, rather than at its own root address. Without a redirect rule, visiting the bare address lands on its mostly blank holding page instead of the login screen.

Q4. Renaming a Homepage tile from Jellyfin to something else, and changing its icon, needs no other change anywhere. Why doesn't this break the connection to Jellyfin?

The tile's name and icon are only a label Homepage displays, never checked against anything. What actually reaches Jellyfin is the href and, for the live widget, the type: jellyfin line, and neither of those changed.

12.Samba: your files, showing up like a plugged-in drive

Everything so far has needed a specific app to reach it, Jellyfin for watching, Pi-hole's own page for DNS settings. This section gives you a far more general kind of access instead: a network folder that shows up in your own computer's file browser exactly like a USB drive plugged into the machine in front of you, except everything inside it actually lives on your server.

Understand this: the same conversation your computer already knows how to have Windows has spoken a file-sharing language called SMB natively for decades, it's the same thing that lets one Windows PC see another's shared folder on an office network. Samba is the piece of software that lets a Linux machine, your server, join that same conversation and offer its own folders exactly the same way. Because SMB isn't a trick to reproduce, Windows, Mac and even most phones already understand it, nothing new needs installing on any of your family's own devices.

Step A, build a plain container for it

Samba has no ready-made helper script the way Pi-hole or Jellyfin did, so this one starts from a bare container instead, the same way you'd start any Linux box before choosing what to run on it. From the Proxmox host Shell:

bash -c "$(curl -fsSL https://raw.githubusercontent.com/community-scripts/ProxmoxVE/main/ct/debian.sh)"
  1. Choose Advanced settings when it asks, and give it 1 core, 1GB memory and 4GB disk. Samba itself is light, it's only handing files back and forth, not storing or converting anything itself.
  2. When it finishes, write down the container's ID and address, and set a DHCP reservation for it in your router, same habit as every other container.

Step B, install Samba

  1. Enter the new container and install it: pct enter <its-id> apt update && apt install -y samba
    Nothing unfamiliar here: the same apt you met back in the first Linux section, asking the package manager for one more piece of software, this time the Samba server itself rather than a whole app.

Step C, open the same doorway you already know

  1. From the Proxmox host Shell, bind your big drive into this container exactly the way you did for Jellyfin in the storage section: pct set <its-id> -mp0 /mnt/media,mp=/media pct reboot <its-id>
    The same trick, a second time: this is the identical bind mount from the storage section, just aimed at a new container. The host's /mnt/media now appears inside this container too, at /media, alongside Jellyfin, which sees the very same files through its own separate doorway.
    Watch for the same permission snag from the storage section. If the folder appears empty or refuses access once you get to testing a share below, it's the identical unprivileged-container ownership mismatch you already read about there, not a new problem.

Step D, define the share

  1. Open Samba's own settings file: nano /etc/samba/smb.conf

    Scroll to the very bottom and add this:

    [media] path = /media browsable = yes read only = no guest ok = no valid users = nadri

    Save with Ctrl+O, Enter, then exit with Ctrl+X.

    Reading it: [media] is the name that shows up on your family's computers, call it whatever you like. path is which real folder it hands out. browsable means it appears when someone looks at what your server offers, rather than only working if typed exactly. read only = no allows dropping files in as well as taking them out. guest ok = no means a password is required, and valid users names exactly who that can be, swap nadri for whatever name you want your Samba account to be.
    Why not guest ok = yes: that setting lets anyone on your network in with no password at all. Fine for a public library terminal, not for a folder that will hold family photos and documents. A password costs one extra step at setup and buys real protection for something worth protecting.
  2. Create the actual account Samba checks that password against: adduser --no-create-home --disabled-password nadri smbpasswd -a nadri

    It asks for a password twice. This is the one your family types when connecting, so pick something you're happy sharing with them, and write it in your notes.

    Two separate accounts doing two separate jobs: adduser makes an ordinary Linux user, which Samba requires as a base to attach to, even though nobody is ever going to log into this container as that user directly, which is why --no-create-home and --disabled-password switch off the parts of a normal account you don't need. smbpasswd then gives that same name a second, separate password, the one Samba actually checks, kept in its own store rather than reusing Linux's own login system.
  3. Restart Samba so it reads the new file: systemctl restart smbd

Step E, connect from an actual computer

  1. On Windows, open File Explorer, and in the address bar type \\<its-ip>\media. On a Mac, open Finder, choose Go, Connect to Server, and type smb://<its-ip>/media. Sign in with the username and password from the step above.
    You'll see: the folder opens exactly like a local drive. Drag a file in from your desktop, and it appears back on the server's /mnt/media immediately, no upload page, no app.
You'll meet this again SMB/Samba file shares are still exactly how most offices hand out shared drives today, and the split you just built by hand, a Linux service account holding its own separate credential rather than a person's own login, is the same pattern behind every service principal and service account you'll meet running real infrastructure.
Recap
  • Samba lets a Linux server speak the same file-sharing language, SMB, that Windows, Mac and most phones already understand natively, so no new software is needed on any device to use it.
  • The same bind mount from the storage section can be reused to give a second container, this one, its own doorway onto the same big drive Jellyfin already uses.
  • Samba checks its own separate password store, layered on top of an ordinary Linux user created just to anchor it, rather than reusing Linux's own login.
Check yourself

Q1. Why does connecting to this share need no extra app on a Windows or Mac computer?

Both already speak SMB, the same file-sharing protocol Samba uses, natively, since it's the same language Windows PCs have long used to share folders with each other. Samba just lets a Linux machine join that same conversation.

Q2. Why create a Linux user at all if nobody is meant to log into the container as them?

Samba needs an existing Linux account to attach its own separate password to, even though the account itself is never used for an actual login, which is why the home directory and normal login are switched off when it's created.

Q3. What would guest ok = yes actually do, and why is it avoided here?

It would let anyone on the network open the share with no password at all. Fine for something genuinely public, but not appropriate for a share that will hold family files.

13.Nextcloud: the same files, but with history, sharing and an app

The share you just built is deliberately simple: a folder that appears on other machines. This one sits alongside it and does the job Google Drive or Dropbox does, which is a different job than it first appears. You'll also meet a new way of getting software, one where somebody else has already assembled the whole thing for you.

Why build this when the last section already shared your files It's a fair question, and the answer is that Samba shares a folder while Nextcloud manages files, which sound the same and are not. Samba gives you a drive on the network: open it, drag things in, done. If somebody saves over a document, the old version is gone. If your dad wants to send a file to someone outside the house, he can't, because the share only exists on your network. If your phone is on mobile data, it can't see the share at all.

Nextcloud keeps previous versions of every file, so overwriting something is undoable. It has a proper recycle bin. It hands out share links that work from anywhere. It has phone and desktop apps that sync a folder continuously, the way Dropbox does, rather than needing you to be connected to a share. And it has accounts, so each person gets their own space plus whatever is deliberately shared.

The honest trade: it's a full web application with a database behind it, so it's heavier and there is more that can go wrong. Samba is a folder. If all you'll ever do is drag films onto a drive, Samba was already enough and skipping this section costs you nothing.
Understand this: an appliance, which is a third way of getting software So far you've met two ways to get an app running. You built one by hand (Pi-hole: make an empty container, install into it, configure it). You ran helper scripts that did that same work for you (Jellyfin, Homepage, and the rest). This section introduces the third: an appliance.

An appliance isn't installed at all. Somebody else already built the whole machine, operating system, web server, database, the app and its configuration all assembled and tested together, then saved the finished result as a template, which is a frozen copy of an entire working system. You don't install anything. You stamp out a copy of theirs and switch it on.

TurnKey Linux is a long-running project that publishes about a hundred of these, and Proxmox carries their catalogue built in, which is why nothing here downloads from a stranger's website. The trade is the usual one: an appliance is the fastest and most reliable route to a working system, and in exchange you learn less about the software's insides and you accept how somebody else chose to arrange it. That's a reasonable deal for Nextcloud specifically, because installing it by hand means setting up a web server, a database, a PHP runtime and a pile of tuning, which is a lot of fiddling for very little insight.

This idea scales up almost exactly. Every cloud provider runs a marketplace of prebuilt machine images for the same reason, and picking one instead of building from bare metal is the same decision with the same trade.

Step A, create the appliance

  1. From the Proxmox host Shell, first check the appliance you want is actually in the catalogue: pveam available --section turnkeylinux | grep -i nextcloud
    You'll see: one line naming a template file, something like debian-12-turnkey-nextcloud_18.1-1_amd64.tar.gz. If you see nothing at all, run pveam update first to refresh the catalogue and try again.
    Why check before doing anything: the script in the next step builds its menu from this exact list. Ten seconds here tells you whether the rest of the section is going to work, which is a much better place to find out than halfway through a wizard.
  2. Run the helper that wraps the whole thing: bash -c "$(curl -fsSL https://raw.githubusercontent.com/community-scripts/ProxmoxVE/main/turnkey/turnkey.sh)"
    You'll see: a blue menu listing every TurnKey appliance available. Scroll to nextcloud, select it, then answer three short questions: which storage pool to use, which container ID to give it (accept the number it suggests), and a hostname (nextcloud is fine). It then downloads the template, which takes a minute or two the first time, builds the container and starts it.
    What this script is and isn't doing: unlike the other community scripts you've run, this one installs no software whatsoever. Proxmox can already deploy TurnKey templates on its own; this just puts a menu in front of a job that would otherwise be several commands with long filenames in them. Everything it creates is an ordinary unprivileged container exactly like the ones you built yourself.
  3. Read the last few lines it prints and write down the IP address, the login (root) and the password it generated. It also saves that password to a file on the host, which you can read back at any time: cat ~/turnkey-nextcloud.creds
    Why it generated one rather than asking you: a random password means the appliance is never sitting there with a default that everybody on the internet knows. It's the same reasoning as the guide's earlier habit of not leaving anything on a known default. Note it lives on the host, in root's home folder, not inside the container.
  4. Set a DHCP reservation for it in your router, the same habit as every other container.
    Why it matters more here: Nextcloud writes its own address into its configuration and refuses connections that arrive under a name it doesn't recognise, as a security measure. An address that changes underneath it turns into a locked door with a confusing error behind it.

Step B, finish the setup in the container's console

What "console" means here Everything you've run so far, you ran through the Shell button on the Proxmox host, then reached apps through a web page. This appliance is different: the first time it boots, it runs a setup wizard on its own screen, and the only way to see that screen is to open the container's own console. In the Proxmox web page, click the container in the left-hand list, then Console. That is a virtual monitor plugged into that container, exactly as if you'd walked over to a physical machine and looked at it.
  1. Open the container's Console. The wizard is either already waiting or appears within a few seconds of the container finishing its first boot. Work through its questions, which it asks one screen at a time:
    • A password for the Nextcloud admin account. This is the one you'll actually use every day, so make it a real one and put it in your notes file.
    • A password for the database (it may call this MySQL or MariaDB). You will almost certainly never type this again, so let it be long and forgettable, but still write it down.
    • An email address for the admin account, and possibly a domain name. Where it asks for a domain, put the container's IP address.
    • Offers to register with the TurnKey Hub, install security updates, and similar. Declining the hub is fine. Accepting security updates is worth doing.
    Check your keyboard before typing a password here. This console is not a web page and it may assume a US keyboard layout regardless of yours. On a UK keyboard that quietly swaps a few symbols, notably @ and ", and £ may not exist at all. The screen shows dots either way, so you find out later, at a login box, with no idea why. Sticking to letters and numbers for these first passwords sidesteps it entirely, and you can change them to anything you like afterwards from inside the web page where the keyboard behaves normally.
  2. When the wizard finishes it drops you at an ordinary login prompt. Leave it there and go back to your browser.

Step C, first login

  1. Visit https://<its-ip> in a browser. Note the s: this appliance serves on HTTPS, port 443, and will not answer plain http in the usual way.
    You'll see: the same "your connection is not private" warning you met when you first opened Proxmox. Same cause, a self-signed certificate, and the same answer: click through the advanced option and continue. It's your own machine on your own network.
  2. Log in as admin with the Nextcloud password from Step B.
    You'll see: the Nextcloud files page, with a few sample documents in it. Delete them whenever you like.
Three other doors this appliance leaves open Alongside the main page, TurnKey appliances also serve a system control panel on port 12321, a database editor on 12322, and a web-based terminal on 12320. You do not need any of them, and every one of them is another way in, so it's worth knowing they exist rather than discovering them by accident later. Leaving them alone is fine on your own network. If you ever expose this container beyond it, they are the first thing to shut off.

Step D, put the actual files on the big drive

Understand this: two numbers for the same user This container was built with 8GB of disk, which is fine for the software and hopeless for a family's documents. So you'll do the same bind mount you already know from the storage section, and then meet the snag that section warned you about, properly this time.

This container is unprivileged, which means the user accounts inside it are not the same as the user accounts outside it. Proxmox shifts every one of them by 100000. The web server inside runs as a user numbered 33, so as far as the host is concerned, the thing writing those files is user 100033. Neither number is wrong, they're the same account seen from two sides of a wall.

This is why chown run from inside the container fails with "Operation not permitted", and why the fix has to be run from the host using the shifted number. Get this backwards and you get a folder the container can see and cannot write to, which surfaces as a vague error about storage being unavailable rather than anything about permissions.
  1. From the host, make the folder and hand it to the right user: mkdir -p /mnt/media/nextcloud chown -R 100033:100033 /mnt/media/nextcloud
  2. Still on the host, attach it into the container and restart, using its ID from Step A: pct set <its-id> -mp0 /mnt/media/nextcloud,mp=/mnt/ncdata pct reboot <its-id>
    Reading it again, since this is the third time: -mp0 is which mount slot, /mnt/media/nextcloud is the real folder on the host, and mp=/mnt/ncdata is the name you're inventing for how it appears inside. The first path already exists; the second one doesn't until this command runs.
  3. Get inside the container and find where Nextcloud currently keeps its files: pct enter <its-id> grep datadirectory /var/www/nextcloud/config/config.php
    You'll see: a line reading something like 'datadirectory' => '/var/www/nextcloud/data',. If instead you get "No such file or directory", the appliance has put things somewhere else, and find / -name config.php -path "*nextcloud*" 2>/dev/null will tell you where.
  4. Stop the web server, move what's there onto the drive, and point the configuration at the new home: systemctl stop apache2 cp -a /var/www/nextcloud/data/. /mnt/ncdata/ nano /var/www/nextcloud/config/config.php Change the datadirectory line to read 'datadirectory' => '/mnt/ncdata', and save with Ctrl+O, Enter, Ctrl+X. Then start it again: systemctl start apache2
    Why stop it first: copying files out from under a running application is how you end up with half a file. Stopping it for the ten seconds this takes removes the entire category of problem. This is the same instinct as snapshotting before a change, just at a smaller scale.
    Why cp -a and the dot: the -a preserves ownership and permissions rather than making everything belong to whoever ran the command, which matters enormously here. The trailing /. means "the contents of this folder" rather than the folder itself, which is the difference between filling /mnt/ncdata and creating /mnt/ncdata/data inside it.
  5. Reload the Nextcloud page in your browser and confirm it still works, then check the space it thinks it has: df -h /mnt/ncdata
    You'll see: the size of your big drive rather than the container's small disk. That's the whole point of this step, so it's worth actually looking.

Step E, accounts and the apps

  1. In Nextcloud, click your avatar top right, then Users. Add one account per person. You can set a quota per person, which caps how much of the drive each of them can fill.
    Why separate accounts rather than one shared login: each person gets a private space by default, sharing becomes something you choose rather than the only option, and if somebody's laptop is lost you revoke one account instead of changing a password everybody has to relearn. It's the same least-privilege reasoning as the service account in the Samba section, applied to people instead of software.
  2. On each person's phone, install the free Nextcloud app; on laptops, the Nextcloud Desktop client. Both ask for the server address (https://<its-ip>) and that person's login.
    You'll see: the desktop client creates a Nextcloud folder that syncs continuously in the background, and the phone app can be set to upload photos automatically. Away from home, none of this reaches the server unless Tailscale is connected, exactly as with everything else in this build.
You'll meet this again Deploying from a prebuilt image rather than installing from scratch is how most cloud infrastructure actually gets created, and every provider runs a marketplace of them. The UID shifting you did in Step D is the same idea as the identity mapping that shows up whenever one system's users have to be understood by another, which is most of what enterprise identity work turns out to be. And per-user quotas on shared storage are ordinary administration, the same lever a cloud provider pulls on you.
Recap
  • An appliance is a whole prebuilt system saved as a template and stamped out rather than installed. Fastest route to something working, at the cost of learning the software's insides.
  • Nextcloud does a different job from Samba: version history, a recycle bin, share links, sync apps and per-person accounts, in exchange for being much heavier than a shared folder.
  • Unprivileged containers shift their user numbers by 100000, so ownership on shared folders has to be fixed from the host using the shifted number, never from inside.
  • Moving an app's data means moving the files and telling the app where they went. Doing only one of the two is the usual mistake.
Check yourself

Q1. What's the practical difference between an appliance and the helper scripts you ran earlier?

A helper script installs software into a fresh container, step by step, on your machine. An appliance is a complete system somebody already built and tested, saved as a template, so nothing is installed at all, you just deploy a copy of theirs.

Q2. The web server inside the container runs as user 33. Why does chown 33:33 from the host not do what you want?

Because the container is unprivileged, so its users are shifted by 100000 on the host side. From the host, that user is 100033. Using 33 would hand the folder to a completely different account.

Q3. You bind mounted the drive in and copied the files across, but Nextcloud still reports it's nearly full. What did you miss?

The datadirectory line in config.php. The files moved, but the application was never told, so it's still reading and writing to the old location on the small container disk.

14.Ops discipline: the habits that separate hobbyists from pros

You now have a real, working system that the household relies on. These are the habits that keep it healthy, and they're the same disciplines that separate a hobbyist from someone doing this professionally. Build them in now, before you go adding more.

Understand this: a snapshot is not a backup A snapshot saves a container's state on the same disk: brilliant for "undo my change", useless if the disk itself dies. A backup is a separate copy kept elsewhere. Pros follow the 3-2-1 rule: 3 copies of important data, on 2 different media, with 1 kept off-site. Even a mirror of two drives isn't a backup, because deleting a file deletes it on both. This distinction is a genuine exam and interview topic.
  • Snapshot before every change (container → Snapshots → Take Snapshot). Ten-second undo.
  • Document everything in your notes file: IPs, ports, passwords, what each container does. Ops teams live and die by good documentation.
  • Patch regularly. Security patches are basic hygiene, and the automation below means you no longer have to remember to apply them yourself.
  • Least privilege: don't run things as root when you don't need to, and prefer "unprivileged" containers. Giving software only the access it needs is a core security principle.
  • Nothing is exposed unless you deliberately port-forward, which we never do.

Automating the patching, since remembering isn't a strategy

Understand this: two very different kinds of update A security patch fixes a known hole in something you already have, small, frequent, and low risk to apply, the software works the same way afterwards, just with the hole closed. A version upgrade changes what the software actually does, new features, new behaviour, occasionally something that used to work no longer working quite the same way. The first kind is safe to automate completely. The second is worth a deliberate look before it happens, which is exactly why real operations teams automate one and not the other.
  1. Install and switch on automatic security patching inside a container, using Pi-hole's as the example: pct exec 100 -- bash -c "apt update && apt install -y unattended-upgrades && dpkg-reconfigure -f noninteractive unattended-upgrades"
    What each part is doing: unattended-upgrades is a small program, standard on Debian and Ubuntu, whose only job is to quietly check for and install security patches on a timer, the same idea as your phone patching itself overnight without asking. dpkg-reconfigure -f noninteractive is how you answer a package's setup questions from a script rather than by hand, -f noninteractive meaning "use sensible defaults instead of asking me anything." Once this has run, that one container keeps its own known security holes closed without you doing anything else, ever again.
  2. Repeat it across every container in one go, rather than typing it out separately for each, from the Proxmox host Shell: for id in $(pct list | awk 'NR>1{print $1}'); do pct exec $id -- bash -c "apt update && apt install -y unattended-upgrades && dpkg-reconfigure -f noninteractive unattended-upgrades" done
    Reading the loop: pct list prints every container you have, one per line, with a header row on top. awk 'NR>1{print $1}' throws away that header row and keeps only the first column of what's left, the ID numbers. for id in $(...) then runs everything between do and done once for each of those IDs in turn, plugging each one in as $id. The practical effect: one command, typed once, quietly visits every container you own and switches this on inside each.
  3. Leave the Proxmox host itself out of that loop, it isn't a container pct can reach, and it deserves more caution anyway. If you want the same protection there, install it the same way directly in the host Shell, but add one more line afterwards: echo 'Unattended-Upgrade::Automatic-Reboot "false";' >> /etc/apt/apt.conf.d/50unattended-upgrades
    Why the host gets one line the containers didn't: a security patch on Pi-hole or Jellyfin restarting that one service is a non-event nobody notices. Proxmox rebooting itself takes every container down with it, all at once, with nobody watching. This line stops it from ever rebooting itself automatically; a patch that needs a reboot just waits, quietly flagged, until you do it yourself on your own schedule. Keep an eye on the host's own Updates tab in its web interface every so often regardless, since Proxmox's own version upgrades, unlike plain security patches, are exactly the kind of change worth reading about before applying.
What this doesn't cover This patches the operating system underneath each app, not the app itself. Jellyfin, Pi-hole and everything else still only move to a new version when you deliberately re-run that container's own install script, exactly as this guide already has you doing elsewhere. That's the deliberate half of the split above, left in your hands on purpose rather than automated away.

When a container quietly fills its own disk

Understand this: the container is up, the app is dead, and that is one fault not two This is the single most common way a home server breaks, and the reason it catches people out is that the machine keeps insisting everything is fine. Each container was given its own small disk when it was created, often eight gigabytes, and that disk holds the operating system, the app, and everything the app writes as it runs. The container itself needs almost nothing to stay running. The app inside it needs to write constantly.

So when that disk fills, the container carries on reporting itself as running while the app inside dies within a second of starting, because the first thing it tries to do is open its database and it cannot. It gets restarted, dies again, and after a handful of attempts the system decides the service is flapping and stops trying, at which point everything goes quiet and you get no further clues at all.

The reason it usually happens after a reboot rather than during normal use is simply that a reboot is the next time anything tries to start from scratch. The disk had been filling for weeks; the reboot is when you find out.
  1. Get inside the container and look at the disk before touching anything. pct enter <its-id> df -h /
    You'll see: a percentage. Anything from about 95% upwards is your answer and you can stop looking for other causes.
  2. Ask the service what happened, in its own words. systemctl status <app-name> --no-pager -l
    What you're reading for: a line saying failed, a Duration measured in milliseconds, and a mention of the start request being repeated too quickly. Together those three say the app is not crashing part way through its work, it is dying immediately on startup, which points at something it needs before it can do anything rather than at anything it was asked to do.
  3. Find where the space actually went, so you delete the right thing rather than the first thing. du -xh --max-depth=1 / 2>/dev/null | sort -h | tail -15
    Why the -x matters: it tells the count to stop at the edge of this disk. Without it, any big drive you have mounted inside the container gets included, the totals come back in terabytes, and the actual culprit is buried. Add another --max-depth run on whichever folder came out largest to walk further in.
  4. Reclaim the safe things. None of these touch anything the app owns. apt clean journalctl --vacuum-size=50M
    Why the package cache is nearly always the answer: every package you have ever installed or upgraded leaves its downloaded installer sitting in a cache folder, and nothing ever clears it. On a machine with a large disk you would never notice. On an eight gigabyte container it is fatal, and the automatic security patching set up earlier in this section quietly makes it worse, because it downloads installers on your behalf for years without ever being asked to tidy up. apt clean deletes those installers only. Nothing that is installed is affected, because the installer and the installed thing are two separate things.
    You'll see: df -h / reporting gigabytes free where it reported megabytes before.
  5. Clear the flapping mark, then start the app. systemctl reset-failed <app-name> systemctl start <app-name> systemctl status <app-name> --no-pager
    The first of those three lines is not optional. Having given up earlier, the system is refusing to accept start requests for that service at all. Without clearing that, your start command appears to do nothing whatsoever, with no error, and you conclude the fix failed when it worked.
  6. Now stop it happening again. Leave the container, and from the host give it more room. pct resize <its-id> rootfs +16G
    Why this is safe to do while it is running: growing a disk only adds unused space at the end of it. Nothing already written is moved or rewritten, so there is nothing to lose and no need to stop the app. Shrinking one is an entirely different and genuinely dangerous operation, which is why Proxmox will not do it.
    Why to bother when you just freed the space: because you have not fixed anything, you have bought time. Eight gigabytes was too small for the job from the start, and the same cache will fill it again. This is the difference between clearing a blockage and widening the pipe.
Worth doing before anything is broken Run df -h / inside each container occasionally, or put a disk usage tile on the dashboard you built earlier. Every fault in this subsection is trivially avoidable and completely invisible until the moment it takes a service down, which is a bad combination to leave unwatched.
Recap
  • Snapshots undo changes; backups (3-2-1) survive disasters. They're different.
  • Security patches are safe to automate completely, unattended-upgrades quietly handles this on a timer in every container, and can be pushed into all of them at once with a single loop from the host. Version upgrades change behaviour and are worth a deliberate look first, which is why they're left alone rather than automated the same way.
  • The Proxmox host gets the same protection but with automatic reboots switched off, since a container restarting is a non-event while the host restarting takes everything down at once.
  • Documentation, regular patching, and least privilege are the everyday disciplines of real operations and security work.

17.Glossary of every term you'll meet

Fladder
An alternative app for watching your Jellyfin library, built by a different team. Talks to the same server, no changes needed on Jellyfin's side.
Homepage
A dashboard container that shows every one of your services as a clickable tile, so nobody needs to know an IP address or port to reach anything. Configured entirely through plain text files like services.yaml rather than clicked together in a web page.
Samba / SMB
SMB is the file-sharing language Windows, Mac and most phones already speak natively. Samba is the software that lets a Linux server join that same conversation, so a folder on it shows up on other devices exactly like a plugged-in drive, no extra app needed.
Local DNS record
A name-to-address entry you add to Pi-hole yourself, only known inside your own house, letting a memorable name like nadrihome.com replace an IP address. Ending it in a real TLD like .com keeps browsers from treating it as a search. Can only ever hold a bare address, never a port or protocol.
Reverse proxy
A container (here, Nginx Proxy Manager) that sits on the normal web port and forwards each incoming name on to the right internal container and port, which is what lets a name work with no port typed after it.
HTTP status code / 301 redirect
A three-digit number every web response carries, telling the browser what happened. 301 means "moved permanently", telling the browser to automatically continue on to a new address, used here to send a bare address on to a service's real path like /admin.
Gelato
A Jellyfin plugin that fills your library catalogue with entries for thousands of titles and, when you press play, fetches a real stream on demand rather than storing anything. Needs Jellyfin 10.11 or newer.
AIOStreams
An adapter that gathers many separate streaming sources into one tidy, de-duplicated feed for Gelato to read from. The one piece of this route that runs as a container on your own machine.
Debrid / TorBox
A paid service that keeps a large pile of already fetched content on fast servers and serves it over an ordinary web connection, which is what makes on-demand playback instant with no seeding or stalling. TorBox is the one this build uses.
Stub file
A small file that stands in for something real. Gelato writes exactly one, called stub.txt, into each of its two folders, purely so Jellyfin has something to find and will scan the folder. The titles themselves are database entries, not files.
Manifest
The single web address AIOStreams produces once configured, which you paste into Gelato so the plugin knows where to pull its catalogue and streams from.
Docker / Docker Compose
Docker runs small, lightweight app packages (container images) inside one Linux container, sharing its resources rather than each getting a full separate one. Docker Compose is a single recipe file (docker-compose.yml) listing every app to run, what to give it access to, and how they connect, applied in one command.
Immich / Vaultwarden / Home Assistant / Uptime Kuma / Proxmox Backup Server
Future containers on the roadmap: private photo backup, a shared password manager, smart home control, a dashboard that watches your other containers, and a proper off-site backup system.
Hypervisor
Software that runs multiple virtual computers on one physical machine. Proxmox is a Type 1 (bare-metal) one.
Virtual machine (VM)
A software "computer" that runs its own full operating system on a hypervisor.
Container / LXC
A lighter isolated environment that shares the host's Linux kernel. Docker and Kubernetes are the industry versions.
Template / image
A pre-built base OS a container or VM is created from.
Linux
The open-source operating system running most servers and clouds. Debian is the flavour under Proxmox.
Shell / terminal / CLI
The text command-line interface for controlling a computer by typing.
root
The all-powerful administrator account on Linux.
Package manager / apt / repository
The tool (apt) that installs software from curated online libraries (repositories), handling dependencies.
IP address
A device's network number. Private ones (192.168.x, 10.x, 172.16-31.x) only work inside your network.
DNS
The internet's phone book: turns names into IP addresses. Runs on port 53.
DHCP
The service that automatically hands out IP addresses to devices joining a network.
Port
A number identifying a specific service on a machine (Proxmox 8006, DNS 53, Jellyfin 8096).
NAT
Network Address Translation: lets many private devices share one public IP, and blocks uninvited inbound traffic.
Firewall
Filters network traffic by rules. A stateful one only allows replies to connections you started.
Port forwarding
Deliberately opening a service to the internet through the firewall. Risky; we avoid it.
VPN / WireGuard / Tailscale
An encrypted private network over the internet for your own devices. Tailscale uses the WireGuard protocol.
CIDR (e.g. /24)
Notation for a block of IP addresses; /24 = 256 addresses. Used to define cloud networks too.
Zero-trust
Security approach: trust no network by default, verify every device. Tailscale is an example.
IP forwarding
A Linux setting, separate from Tailscale itself, controlling whether a machine is allowed to pass traffic through to other devices rather than only handling traffic meant for itself. Off by default; needs enabling for subnet routing to actually work.
Global Nameserver (Tailscale DNS)
A DNS address that Tailscale hands out to every device in the tailnet, the same role a home router's DHCP normally plays for devices connected to it locally. Needed so devices that are only ever reachable through the tunnel (like a phone away from home) still know to ask Pi-hole for custom domain names instead of falling back to the public internet's DNS.
Client / server
The server provides a service; the client consumes it. The pattern behind most software.
Direct play
The good outcome when you press play: the server hands the video file over exactly as it is and the app on your device decodes it. The server does almost no work, and this is what everything in this guide is arranged to achieve.
Transcoding
The fallback: the server rebuilds the video into a different format on the fly because the app can't handle the original. Expensive, and the cause of most stuttering and buffering. Usually triggered by a weak app rather than a weak server.
Quick Sync
A dedicated video-processing circuit built into Intel chips that handles transcoding far more efficiently than the main processor. Worth switching on as a safety net, but it makes the fallback cheaper rather than unnecessary.
MPV
A playback engine that decodes essentially any video format, including image-based subtitles. Apps built around it (Streamyfin, Findroid, Jellyfin Media Player) direct play almost everything, which is why they're named specifically rather than left to preference.
Remux
An untouched copy straight from a disc with nothing compressed, often 60GB or more for a single film. Refused deliberately in the AIOStreams size filter, since nothing in a normal house benefits from moving that much data in real time.
Encode (AVC, HEVC, AV1)
The method used to squeeze video down before sending it. AVC is the old one everything can play, HEVC is the newer one every current screen handles, and AV1 is the cleverest but is refused in this build because most televisions and older phones cannot decode it and hand the work back to the server.
Dolby Vision / DV Only
A brighter, richer colour format. Usually carried as an extra layer over an ordinary picture, so screens that don't understand it look normal anyway. Files tagged DV Only have no ordinary picture underneath and come out green and purple on those screens, which is why only that case is excluded.
ASS / SSA subtitles
Styled text subtitles, standard in anime, carrying their own fonts, positions and colours so signs in the scene can be labelled. Real text rather than pictures, but drawing them needs a typesetting engine, and an app without one makes the server burn them into the picture instead.
Appliance / template
A complete prebuilt system, operating system and application and configuration all assembled and tested together, saved as a frozen copy you stamp out rather than install. TurnKey Linux publishes about a hundred of them and Proxmox carries the catalogue built in.
Nextcloud
Your own version of Google Drive or Dropbox: file sync, version history, a recycle bin, share links and per-person accounts. Heavier than a plain Samba share, and doing a genuinely different job.
Snapshot vs backup
A snapshot is an on-disk undo point; a backup is a separate copy elsewhere (see 3-2-1).
Headless
A machine run with no monitor/keyboard, managed remotely over the network.
IaaS
Infrastructure as a Service: renting virtual machines/networks from a cloud. An AZ-900 topic you've now built by hand.
